# 시나리오 테스트: 배경

규칙은 이 디렉터리의 `AGENTS.md`, 구성은 `README.md` 에 있다.

## 템플릿 데이터베이스에 무엇이 있는가

스키마만 있다. row 는 하나도 없다.

131개 테이블의 DDL 은 비용이 크고 복제는 비용이 작아서 템플릿을 둔다. `CREATE DATABASE ... TEMPLATE` 으로
테스트마다 복제한다. 다른 용도는 없고, 다른 용도를 추가하지 않는다.

row 가 하나라도 있으면 어디까지가 공통 배경이고 어디부터가 시나리오의 전제인지 정해야 한다. 이 경계는 항상
모호해지고, 시나리오는 의존하지 않는다고 생각한 것에 의존하게 된다.

## 왜 공유 배경을 제거했는가

처음에는 템플릿에 사용자 4명, 도메인 1개, 프로젝트 1개, 정책 3개를 미리 저장했다. 여기서 문제가 4가지 생겼다.

- 페르소나 이름 하나가 서로 무관한 4가지를 동시에 의미했다: 어느 사용자 row 인지, 그 row 의 레거시 역할
  column 값, 어느 프로젝트의 멤버 목록에 있는지, 어떤 RBAC 권한을 받았는지. 시나리오 표에는 마지막 것만 보였다.
- 시나리오가 자기 전제를 변경할 수 없었다. 다른 역할이 필요하면 공유 배경을 수정해야 했고, 그러면 다른
  시나리오도 영향을 받았다.
- 어떤 시나리오도 사용하지 않는 row 가 모든 시나리오의 의존성이 되었다.
- 공유 배경이 필요한 값을 암묵적으로 제공해서, 요청에 무엇이 필요한지 시나리오 표에 드러나지 않았다.

마지막 문제가 가장 컸다. vfolder 하나를 생성하는 데 필요한 것이 4개 더 있었지만, 공유 배경이 제공하는
동안에는 아무도 알지 못했다.

## 왜 adapter 가 아니라 write spec 으로 row 를 미리 저장하는가

상황 준비는 ops 계층의 역할이다. adapter 는 테스트 대상이지 준비 도구가 아니다.

이전 adapter 호출로 상황을 정의하는 안도 제시되었지만 기각했다. 세션 시나리오에 vfolder 가 필요하면 vfolder
adapter 까지 조립하게 되어, 한 시나리오의 의존성이 테스트 대상 밖으로 넓어진다.

대신 시나리오는 `TestSeeder` 의 메서드(`creating`, `adding` 등)로만 row 를 생성한다. 이 메서드들은 모두 src 의
write spec(`Creator`, `Upserter` 등)을 인자로 받는다. 그래서 테스트 코드가 SQL 이나 ORM 으로 row 를 직접
생성할 수 없고, row 는 Manager 가 실제로 사용하는 경로로만 생성된다. 메서드 목록은 `AGENTS.md` 에 있다.

## 사용자 생성은 왜 다른가

사용자 생성은 row 하나로 끝나지 않는다. Manager 는 사용자 row, 그 row 의 그래프 위치, 프리셋이 지정한 역할,
인증에 사용하는 키페어, 개인 프로젝트를 함께 저장한다.

일부만 모방하면 나중에 드러나지 않게 어긋난다. 개인 vfolder 는 소유자를 통해 개인 프로젝트를 찾는데, 그
프로젝트가 없으면 vfolder 가 속할 곳이 없다. 그래서 그 연산 전체를 사용한다.

## 왜 역할 프리셋을 사용하지 않는가

이 테스트가 확인할 것은 권한이 있으면 통과하고 없으면 거부되는지이고, 제공되는 역할 프리셋이 관리자에게 무엇을
주는지는 별개의 문제다. 섞으면 후자가 변경될 때 전자의 테스트가 실패한다.

또한 제공되는 역할 프리셋 4개는 모두 `deleted: true` 라 그대로는 동작하지 않는다. 이를 복원해 사용하면 제품
상태를 우회하게 된다.

## 권한을 부여할 수 없는 엔티티가 있다

도메인이 그렇다. 어느 스코프에도 속하지 않게 생성되고 자기 아래 하위 엔티티를 갖지 않는다. 도메인에 속하는
것은 프로젝트, 사용자, 그들의 vfolder 다.

그래서 도메인 조회 권한을 받은 사용자 같은 시나리오는 성립하지 않는다. 도메인 조회는 전역 superadmin 역할이
결정하고 권한 그래프를 거치지 않는다.

새 컴포넌트의 시나리오를 작성하기 전에 그 엔티티의 creator spec 분기를 먼저 확인한다. 어느 스코프에도 속하지
않는 분기면 권한 시나리오를 작성할 수 없다.

## 격리는 두 계층이다

| 계층 | 범위 |
|---|---|
| postgres 컨테이너 | 테스트 프로세스마다 하나. 풀이 슬롯별로 실행한다 |
| 템플릿 데이터베이스 | 컨테이너마다 하나 |
| 작업 데이터베이스 | 테스트마다 하나. 끝나면 삭제한다 |

row 이름을 난수가 아니라 시나리오별 카운터로 지정하는 근거가 이것이다. 고유해야 하는 범위가 테스트 하나이므로
카운터로 충분하고, 값이 정해져 있어 실패 메시지가 실행마다 같다.

## 시계가 둘이다

타임스탬프는 데이터베이스 서버가 기록하고 비교는 테스트 프로세스가 한다. 저장 직후에 검사하므로 두 시계가
조금만 어긋나도 아직 오지 않은 시각이 된다. 그래서 시간 조건에는 허용 오차가 있다.

조건의 하한은 임의로 고른 시간 폭이 아니라 시나리오 생성을 시작한 시각이다. `TestSeeder` 가 그 시각을 가지고
있고 `since_started` 가 그 시각으로 조건을 만든다. 몇 분 안에 기록되었는지로는 값이 맞는지 알 수 없다.
