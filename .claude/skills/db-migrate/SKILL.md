## Purpose

Check the schema version, then apply or roll back Alembic migrations for Backend.AI components.

**When to use:** after pulling code with new migrations, to check current against head, to apply pending changes, to roll back (downgrade), and for initial setup.

## Parameters

- **component** (optional): `manager` (default), `accountmgr`, `appproxy`
  - Configs: `alembic.ini`, `alembic-accountmgr.ini`, `alembic-appproxy.ini`
- **direction** (optional): `upgrade` (default), `downgrade`
- **target** (optional): `head` (default), `<revision_id>`, relative (`+1`, `-1`)

## Check status

```bash
# manager: shows current and head together
./backend.ai mgr dbschema show

# any component
./py -m alembic -c <config> current   # applied revision
./py -m alembic -c <config> heads     # latest available
```

| State | Meaning | Action |
|---|---|---|
| up-to-date | current equals head | none |
| behind | current is behind head | upgrade (see below) |
| diverged | multiple heads | Reconcile per `alembic/AGENTS.md`: repoint the `down_revision` of your own migration, or add an empty merge migration when main itself has 2 or more heads |
| no revision | current is empty (fresh DB) | upgrade for initial setup |

## Apply

```bash
./py -m alembic -c <config> <direction> <target>

# examples
./py -m alembic -c alembic.ini upgrade head            # manager to latest
./py -m alembic -c alembic-appproxy.ini upgrade head   # appproxy
./py -m alembic -c alembic.ini downgrade -1            # roll back one revision
./py -m alembic -c alembic.ini upgrade abc123def456    # specific revision
```

Check the status again afterwards. A downgrade may remove data or features, so verify application compatibility.

## Error handling

| Symptom | Cause | Action |
|---|---|---|
| Multiple heads detected | diverged migrations | Reconcile per `alembic/AGENTS.md`, then retry |
| Cannot locate revision 'X' | bad revision id or wrong config | `./py -m alembic -c <config> history`; check the spelling and the component |
| Foreign key constraint violation | existing data blocks the change | Review the data-migration logic of the migration, fix data integrity; manual intervention is often needed |
| Cannot connect (no listener on :5432) | PostgreSQL down or misconfigured | `docker ps \| grep postgres`; see `/halfstack` |
| Migration file not found | code not pulled or wrong branch | `git pull`; verify the branch |

## Safety notes

- Before a downgrade: back up the database, review what data is removed, stop active connections, and do not test on production first.
- After an upgrade: verify key features, restart affected services, and monitor logs for migration errors.
- Commit migrations to Git, test both upgrade and downgrade, review autogenerated migrations, and keep one logical change per migration.

## Workflow integration

- After pulling code: `git pull` → check status → upgrade → start services (`/local-dev`) → verify.
- After authoring a migration (see `alembic/AGENTS.md`): review the file → test upgrade → test downgrade (`--direction=downgrade --target=-1`) → upgrade again → commit.
- Merge conflicts: when the status shows diverged heads, reconcile per `alembic/AGENTS.md` before applying.
