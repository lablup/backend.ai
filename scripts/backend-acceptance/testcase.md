# 백엔드 인수 테스트 — 시나리오와 판정 기준

컨테이너 백엔드(`containerd` / `enroot` / `singularity`) **하나**를 실제 배포에 올렸을 때,
"쓸 수 있는 상태인가"를 판정하기 위한 케이스 모음이다. 여기 있는 케이스는 전부 **실제로 결함을 잡은 적이
있는 것들**이고, 각 항목의 "잡은 것" 열이 그 근거다.

## 전제

| 항목 | 내용 |
|---|---|
| **한 번에 한 백엔드** | 검사 대상 백엔드만 두 노드에서 띄운다. 여러 백엔드를 동시에 띄우면 LOCAL 블록·포트·cgroup이 얽혀 어느 쪽 문제인지 판별할 수 없다 |
| 노드 2개 | 멀티노드 케이스에 필요. 없으면 해당 케이스는 SKIP |
| 실행 위치 | 로컬 노드에서. 원격 노드에는 SSH 무암호 접근 |
| 권한 | `sudo -n` (netns 진입, cgroup·로그 확인) |

```bash
export ACC_IMAGE_ID=... ACC_PROJECT_ID=...     # 필수
export ACC_PEER_HOST=192.168.0.156             # 없으면 멀티노드 케이스는 SKIP
export ACC_START_CMD='...'                     # G2/G3 (에이전트 재기동)에만 필요

./run.sh cd            # containerd 전체
./run.sh en B2 C1 F3   # enroot 특정 케이스만
./run.sh --list
```

케이스는 서로 상태를 물려받는다(B2가 띄운 멀티노드 세션을 C1·C2가 그대로 쓴다). 개별 실행도
되지만 그때는 필요한 세션을 그 케이스가 직접 띄운다.

## A. 기동

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| A1 | 대상 백엔드만 두 노드에서 기동 | 두 에이전트가 ALIVE, **다른 백엔드의 RPC 포트는 닫혀 있음** | 세 백엔드 동시 기동이 LOCAL 블록 0을 서로 뺏어 멀쩡한 세션의 통신을 끊음 |
| A2 | privnet (rootless 전용) | 소켓이 설정된 경로에 생기고 `CapEff`에 `NET_ADMIN,SYS_ADMIN` 포함 | 원격 노드 설정에 `network-privnet-socket`이 없어 기본 경로로 떨어짐 → 에이전트가 `ConnectionRefused`로 죽음 |

## B. 세션 수명주기

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| B1 | 단일노드 세션 | RUNNING 도달 | — |
| B2 | 멀티노드 세션 | RUNNING **그리고 커널이 실제로 두 노드에 갈림** | 자원이 한 노드에 다 들어가면 스케줄러가 패킹한다. 배치를 확인하기 전까지 28회의 "멀티노드 성공"이 전부 단일노드였음 |
| B3 | 연속 기동 (기본 5회, 간격 12초) | 전부 RUNNING, 전부 분산 | 빠른 회전에서만 나타나는 실패가 있었다. 1~2회로는 안 보인다 |
| B4 | 종료 후 잔여물 | repl 소켓 0, 컨테이너 0, 해당 커널의 로그·스크래치 0 | 재시도마다 REPL 소켓 2개가 새어 다음 세션의 커널에 붙음 |

> B2는 **자원으로 분산을 강제**한다: 로컬 노드를 채우는 filler를 먼저 띄워, 두 번째 커널이 원격으로
> 갈 수밖에 없게 만든다. `agent_list` 핀만으로는 부족하다 — 스케줄러는 들어가면 담는다.

## C. 네트워크 (컨테이너 안에서)

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| C1 | 클러스터 DNS | main1·sub1 양쪽 이름이 컨테이너 안에서 해석됨 | 에이전트 재시작 후 피어 이름이 사라짐 |
| C2 | 노드 간 L3 | **DNS가 준 오버레이 주소로** 양방향 0% 손실 | LOCAL 주소(`172.30.x`)는 노드마다 같은 값이라 그걸로 ping하면 **자기 자신**을 친다 |

## D. 격리

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| D1 | seccomp | 커널 프로세스 `Seccomp: 2`, 자식도 상속 | — (런타임 발판 프로세스는 0이 정상. 커널 프로세스를 짚어야 한다) |
| D2 | cgroup 적용 | `memory.max`·`cpuset.cpus`가 **요청한 값과 일치** | 위임 실패 시 `memory.max = max`, `Cpus_allowed_list: 0-31`로 조용히 실행됨 |
| D3 | cgroup 위임 실패 (rootless) | 커널이 **거부**되고 저널·로그·스크래치·cgroup 잔여 0 | 위 상태를 로그만 남기고 띄우고 있었음 |
| D4 | 커널의 cgroup 위치 | 커널이 **에이전트 cgroup 밖**에 있음 | setsid는 프로세스 그룹만 바꾼다. `systemctl stop`은 cgroup으로 죽이므로 위임이 실패한 노드는 커널을 잃는다 |

## E. 스탯

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| E1 | per-container 지표 | `mem`·`io_read`·`net_rx`·`net_tx`·`cpu_used`가 **값으로** 존재 | 지표 키만 보고 "동등"이라 적었다가 값 확인으로 정정 |
| E2 | 매니저 반영 | `occupied_slots`가 요청과 일치 | — |

## F. 로그

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| F1 | 버스트 후 캡 | 파일 ≤5개, 개당 ≤`max_length/5`, 총량이 예산 근처 | — |
| F2 | 지속 부하 피크 | containerd는 예산 이내(하드), rootless는 `4×max_size + rate×5초` 이내(소프트) | rootless 피크가 예산의 3.3배임을 정량화 |
| F3 | 로테이션 가로질러 읽기 | `bai session logs`가 회전된 파일까지 읽어 옴 | — |
| F4 | 무손실 (하드캡 백엔드) | 번호 매긴 줄이 유지 구간 안에서 **결번 없음** | containerd 55,000줄 결번 0으로 확인 |
| F5 | 종료 시 로그 삭제 | 해당 커널의 `.log`+회전분 전부 사라짐 | — |
| F6 | 로그 라이터 실패 (containerd) | 커널이 뜨면 로그 파일이 **반드시 존재** | 라이터가 못 뜨면 커널은 RUNNING인데 출력이 전부 조용히 버려짐 (에러 한 줄 없음) |

## G. 복구

| ID | 시나리오 | 통과 기준 | 잡은 것 |
|---|---|---|---|
| G1 | 에이전트 SIGKILL | 커널 프로세스 생존 | tmux 종료 한 번에 3일짜리 세션의 커널이 같이 죽음 |
| G2 | 재기동 후 | 세션 RUNNING 유지, 커널 생존, 로그 캡 회복 | — |
| G3 | 고아 정리 | 죽은 커널의 로그·스크래치는 제거, **살아있는 커널 것은 보존** | 에이전트가 죽으며 남긴 로그/스크래치를 아무도 안 치움 (실측 4·5개, 12·11·19개) |
| G4 | PID 1 좀비 수거 | 컨테이너 안 좀비 0 | — |

## 케이스 선정 원칙

1. **결과가 아니라 상태를 본다.** "RUNNING"만으로는 부족하다 — 커널이 어느 노드에 갔는지, cgroup에 값이
   들어갔는지, 로그 파일이 생겼는지를 확인한다. 이번에 잡힌 결함 대부분이 "성공처럼 보이는 실패"였다.
2. **살려두는 쪽도 검사한다.** 정리 케이스(B4·G3)는 "지워졌나"뿐 아니라 **"살아있는 것이 남아있나"**를
   같이 본다. 스크래치는 사용자 파일이라 오탐이 곧 데이터 손실이다.
3. **한 번으로 판정하지 않는다.** 간헐적 실패는 반복(B3)에서만 나온다.


## 이 스위트 자체에 대해

첫 실행에서 3건이 실패했는데 **전부 스위트의 결함**이었다. 기록해 둔다 — 같은 함정을 다시 판다:

| 증상 | 실제 원인 |
|---|---|
| D1: "자식이 필터를 상속 못 함" | 커널의 자손을 **명령줄 부분 문자열**로 찾았다. enroot 런처의 argv에는 컨테이너의 마운트 목록과 환경 전체가 들어 있어 커널 엔트리포인트 경로까지 포함한다 → 런처를 커널의 자식으로 오인. 지금은 PPid를 타고 올라가 판정한다 |
| E1: "지표 전부 누락" | 스탯 수집기는 주기로 돈다. 막 뜬 커널에는 아직 시계열이 없다 → 빈 스크레이프를 "누락"으로 판정. 지금은 최대 90초 기다린다 |
| E2: "occupied_slots 불일치" | 에이전트 총량은 그 노드의 **모든 커널** 합이다. 같은 스위트의 다른 케이스가 세션을 잡고 있으면 당연히 안 맞는다. 지금은 "이 세션의 할당이 반영되었는가"만 본다 |
| B2: 멀티노드가 PENDING | filler 크기가 20으로 **고정**이었다. B1의 세션(4)이 살아 있어 로컬에 7밖에 안 남아 8짜리 커널이 못 들어감. 지금은 노드의 실제 여유에서 계산한다 |

검증: enroot 백엔드에서 A1·B1·B2·C1·C2·D1·D2·E1·E2·F1·F3·F5·G4 **13개 전부 통과**.
