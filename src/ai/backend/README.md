# Backend.AI Component Architecture

## Overview

Backend.AI is a modular cloud-native platform that manages AI/ML computing resources. Multiple interconnected components each handle one area of resource management, workload execution, or user interaction.

## System Architecture

### Component Overview

Backend.AI has the following core components:

- **Client**: REST/GraphQL requests through the SDK, CLI, and web UI
- **Webserver**: web UI hosting, the API gateway role, and session management
- **Hive Gateway**: GraphQL federation gateway (GraphQL routing between the Webserver and the Manager)
- **Manager**: API business logic and session/deployment scheduling orchestration
- **App Proxy**: service request routing and load balancing to sessions (kernels)
- **Storage Proxy**: vfolder management and storage backend abstraction
- **Agent**: kernel lifecycle management and resource monitoring on nodes
- **Kernel**: container that runs user work (the Backend.AI abstraction unit)

### Port Number Guide

All port numbers in this document come from the **development environment** (`docker-compose.halfstack.current.yml`) and are generated by the `./scripts/install-dev.sh` script. Production ports depend on the configuration.

#### Backend.AI Component Ports
- **Webserver**: 8090 (HTTP)
- **Manager**: 8091 (HTTP API)
- **Hive Gateway**: 4000 (GraphQL Gateway)
- **Agent RPC**: 6011 (ZeroMQ)
- **Storage Proxy**: 6021 (Client API), 6022 (Manager API)
- **App Proxy Coordinator**: 10200 (HTTP)
- **App Proxy Worker**: 10205-10300 (Traffic Proxy)

#### Internal Ports

Internal ports serve internal requests such as Prometheus metrics collection and service discovery. Only the Prometheus integration exists today.

- **Manager**: 18080 (Prometheus metrics and service discovery)
- **Agent**: 6003 (Prometheus metrics, HTTP service API)
- **Storage Proxy**: 16023 (Prometheus metrics)

**Note**: The internal port is separate from the main API port, so internal monitoring traffic does not mix with user-facing API traffic.

#### Infrastructure Ports
- **PostgreSQL**: 8101 (host) → 5432 (container)
- **Valkey**: 8111 (host) → 6379 (container)
- **etcd**: 8121 (host) → 2379 (container)
- **Prometheus**: 9090
- **Grafana**: 3000

### Flow-Based Architecture

#### 1. Backend.AI API Request Flow

Flow for user calls to Backend.AI APIs such as session creation and resource queries.

```
Client (SDK/CLI/Web UI)
  │
  ├─ REST request ──────→ Webserver ──→ Manager
  │                        (8090)         (8091)
  │
  └─ GraphQL request ───→ Webserver ──→ Hive Router ──→ Manager
                          (8090)         (4000)          (8091)
                                            │
                                            └─ HTTP SSE → WebSocket conversion
                                               (Subscription handling)

Manager
  │
  ├─→ Agent (ZeroMQ RPC): Kernel creation/management
  │
  ├─→ Storage Proxy (HTTP): VFolder management
  │
  └─→ App Proxy Coordinator (HTTP): Circuit registration
```

#### 2. Container Service Access Flow (for example, Jupyter, VSCode)

Flow for user access to services such as Jupyter and VSCode in a created session.

```
User Browser
  │
  └─→ App Proxy Worker (10205-10300) ──→ Kernel (Container)
                                           - Jupyter: 8888
                                           - VSCode: 8180
                                           - Other services

* Worker queries routing information from PostgreSQL/Valkey/etcd
* Worker forwards traffic directly to Kernel on Agent node
```

#### 3. File Upload/Download Flow

Flow for file upload to and download from a vfolder.

```
Client
  │
  └─→ Storage Proxy (6021) ──→ Backend Storage
       - Direct connection          - XFS
       (Bypassing Manager)          - CephFS
                                    - NetApp ONTAP
                                    - PureStorage
```

## Core Components

### [Manager](./manager/)

**Purpose**: central API gateway and orchestrator

The Manager receives REST/GraphQL requests, runs business logic, and centrally triggers the actual work in other components (Agent, Storage Proxy, App Proxy).

**Key responsibilities**:
- Provide the REST/GraphQL API for client requests
- Perform session scheduling per resource group
- Session and deployment orchestration
- User authentication and RBAC authorization
- Metrics collection and the service discovery endpoint

**Key modules**:
- `api/`: REST and GraphQL API endpoints
- `actions/`: Permission validation and monitoring layer
- `services/`: Business logic
- `repositories/`: Data access layer
- `sokovan/`: Session scheduling engine

**Detailed documentation**:

Manager architecture and implementation in depth:

- **[Manager Overview](./manager/README.md)**: Component overview, key responsibilities, and architectural layers
- **[Sokovan Orchestration](./manager/sokovan/README.md)**: Session scheduling orchestrator with 3-tier architecture
  - [Scheduler](./manager/sokovan/scheduler/README.md): Core scheduling engine for session placement
  - [Scheduling Controller](./manager/sokovan/scheduling_controller/README.md): Validation and preparation logic
  - [Deployment Controller](./manager/sokovan/deployment/README.md): Deployment management
- **[Services Layer](./manager/services/README.md)**: Business logic patterns and design principles
- **[Repositories Layer](./manager/repositories/README.md)**: Data access patterns and query optimization
- **[Actions Layer](./manager/actions/README.md)**: Permission validation and monitoring

### [Agent](./agent/)

**Purpose**: kernel lifecycle management on nodes

The Agent receives RPC requests from the Manager, creates and manages kernels (the container abstraction) on nodes, and controls the containers through the Docker backend.

**Key responsibilities**:
- Receive Manager RPC requests and manage the kernel lifecycle (create, start, stop, delete)
- Monitor kernel resource usage (CPU, memory, GPU)
- Report Agent status and resource availability to the Manager
- Manage local scratch storage

**Key modules**:
- `server.py`: RPC endpoints (receive Manager requests)
- `agent.py`: kernel management logic (the Agent's service layer)
- `docker/`: Docker container backend
- `watcher/`: Resource monitoring
- `stats.py`: Statistics collection

### [Storage Proxy](./storage/)

**Purpose**: unified storage backend abstraction

**Key responsibilities**:
- Provide vfolder management
- Abstract multiple storage backends (NFS, CephFS, NetApp, etc.)
- Handle file upload and download
- Manage storage quota and permissions
- Support various enterprise storage solutions

**Key modules**:
- `api/`: Storage management API
- `vfs/`: Virtual filesystem abstraction
- `volumes/`: Volume management
- `storages/`: Backend-specific implementations

### [Webserver](./web/)

**Purpose**: API gateway and web UI hosting

The Webserver provides the web UI and acts as the gateway that proxies all REST/GraphQL requests to the Manager (or the Hive Gateway). It does not handle user authentication directly but manages web sessions.

**Key responsibilities**:
- Serve web UI assets (static files)
- Web session and cookie management
- Proxy REST requests to the Manager
- Proxy GraphQL requests to the Hive Gateway
- Provide security headers and CSRF protection

**Key modules**:
- `auth.py`: Session management logic
- `proxy.py`: Proxy requests to the Manager/Hive Gateway
- `security.py`: Security middleware
- `templates/`: web UI templates

### [App Proxy](./appproxy/)

**Purpose**: service request routing to sessions (kernels)

The App Proxy routes user requests for container services (Jupyter, VSCode, etc.) to the corresponding kernels. The Manager registers circuits through HTTP requests to the App Proxy Coordinator, and users reach kernels through the App Proxy Worker.

**Key responsibilities**:
- Route HTTP/WebSocket traffic to session services
- Load balance across multiple session replicas for model services
- Perform circuit health checks
- Dynamically manage service port mappings

**Components**:
- `coordinator/`: circuit management and health check (the Manager makes HTTP requests)
- `worker/`: Traffic proxy (users connect and the Worker forwards to kernels)
- `common/`: Shared types and utilities

### [Client SDK](./client/)

**Purpose**: Python SDK and CLI for the Backend.AI API

Provides a Python client library and CLI tools that make REST/GraphQL API requests to Backend.AI servers.

**Key responsibilities**:
- Provide a Python client library for API requests
- Implement CLI commands for users and administrators
- Support synchronous and asynchronous API clients

**Key modules**:
- `cli/`: Command-line interface
- `session.py`: Session management API
- `func/`: Functional API wrappers
- `request.py`: HTTP request handling


## Component Dependencies

Components and infrastructure that each component depends on.

### Manager

- **Infrastructure**: PostgreSQL (data storage), Valkey (caching, events, background task management), etcd (global configuration), Prometheus (metrics queries)
- **Components**: Agent (kernel management), Storage Proxy (vfolder management), App Proxy (circuit management)

### Agent

The Agent receives commands only from the Manager and takes no direct requests from users or other components.

- **Infrastructure**: Container Runtime (Docker), Valkey (event delivery, heartbeat, background task management), etcd (global configuration)
- **Components**: Manager (receive RPC commands), Storage Proxy (vfolder mounting)

### Storage Proxy

- **Infrastructure**: Backend Storage (XFS, CephFS, NetApp, etc.), Valkey (optional caching, background task management), etcd (global configuration)
- **Components**: Manager (metadata sync)

### Webserver

- **Infrastructure**: Valkey (web session storage), etcd (global configuration)
- **Components**: Manager (API proxy), Hive Gateway (GraphQL proxy)

### App Proxy

- **Infrastructure**: PostgreSQL (circuit information), Valkey (health check state with the Manager), etcd (Worker discovery, Traefik routing)
- **Components**: Manager (circuit registration), Agent (traffic forwarding)

## Infrastructure

Backend.AI uses several infrastructure components. Each component treats them as required or optional.

### Required Infrastructure (Core Infrastructure)

#### PostgreSQL
- **Purpose**: Persistent data storage (users, sessions, resources, audit logs)
- **Version**: 16.3 or higher
- **Required by**: Manager, App Proxy Coordinator
- **Halfstack port**: 8101
- **Data volume**: `./volumes/postgres-data`
- **Component usage**:
  - Manager: main database (all tables)
  - App Proxy Coordinator: circuit/Worker information (separate schema)

#### Valkey
- **Purpose**: cache, session storage, distributed locks, message queue
- **Version**: 9.1 or higher (Redis-compatible)
- **Required by**: Manager, Webserver
- **Optional by**: Storage Proxy (caching)
- **Halfstack port**: 8111
- **Data volume**: `./volumes/redis-data`
- **Component usage**:
  - Manager: agent state caching, session scheduling, distributed locks
  - Webserver: web session storage (required)
  - Storage Proxy: vfolder metadata caching (optional)

#### etcd
- **Purpose**: global configuration store (easy configuration sharing across all components)
- **Version**: 3.5 or higher
- **Required by**: Manager, App Proxy Coordinator
- **Halfstack port**: 8121
- **Data volume**: `./volumes/etcd-data`
- **Key configuration**:
  - Container registry authentication
  - Storage volume configuration
  - Resource group configuration
  - App Proxy Worker discovery and Traefik routing information

#### Prometheus
- **Purpose**: metrics collection and storage, and the Manager metrics query API
- **Version**: 3.1 or higher
- **Halfstack port**: 9090
- **Components**: Manager (performs metrics queries), Agent, Storage Proxy, Webserver, App Proxy
- **Key features**:
  - Use the Manager service discovery endpoint (`{MANAGER_ADDRESS}/metrics/service_discovery`)
  - Collect directly from every component's `/metrics` endpoint (pull mode, not through the OTEL Collector)
  - Collect per-kernel container metrics
  - Query the collected metrics from the Manager (for internal services)
  - PostgreSQL and Redis Exporter integration

#### Hive Gateway (GraphQL Gateway)
- **Purpose**: GraphQL federation gateway (GraphQL routing between the Webserver and the Manager)
- **Image**: `ghcr.io/graphql-hive/gateway:2.1.12`
- **Halfstack port**: 4000
- **Configuration**: `configs/graphql/gateway.config.ts`
- **Supergraph**: `docs/manager/graphql-reference/supergraph.graphql`
- **Features**:
  - Convert GraphQL Subscription from HTTP SSE → WebSocket
  - REST requests also support HTTP SSE
  - Requires Node.js v20+

### Production Environment Considerations

#### High Availability
- **PostgreSQL**: Primary-Replica replication
- **Valkey**: Valkey Sentinel. Cluster mode is not supported.
- **etcd**: 3+ node cluster
- **App Proxy Coordinator**: Active-Standby

#### Backup and Recovery
- **PostgreSQL**: pg_dump or WAL archiving
- **Valkey**: RDB or AOF snapshots
- **etcd**: Periodic snapshots

#### Monitoring

The Manager provides a Prometheus service discovery endpoint (`{MANAGER_ADDRESS}/metrics/service_discovery`) that automates metrics collection configuration for all components.

- **Prometheus**: Automatically collect all component metrics through the Manager service discovery
- **Alertmanager**: Prometheus alerts
- **Grafana Alerting**: Dashboard-based alerts
- **Uptime**: Service availability monitoring
