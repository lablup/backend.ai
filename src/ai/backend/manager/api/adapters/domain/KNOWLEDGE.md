# 도메인 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 것과 실행 결과가 어긋나면 문장을 먼저
의심한다.

도메인에는 권한 그래프로 권한을 줄 수 없다. 어느 스코프에도 속하지 않게 만들어지고 자기 아래
하위 엔티티를 갖지 않는다. 그래서 생성과 전체 조회는 전역 superadmin 역할이 지키고, 개별
도메인을 읽고 고치는 문은 권한 그래프가 지킨다. 두 문이 서로 다른 것으로 거부하므로 짝을 따로
적는다. 권한을 받은 사용자가 나오는 곳은 리소스 그룹 범위의 조회뿐이다.

공통 계약(대상 존재, 일괄 구성, 페이지)은 프레임워크 계약 테스트가 확인한다. 여기에는 연산마다
대표 성공과 대표 실패, 그리고 도메인 규칙이 만드는 차이만 적는다.

## 만들기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름과 설명만 주고 만든다 | 도메인 없음 | 만들기 | 요청에 없던 값이 기본값으로 채워진 노드 전체 |
| 만들면 model-store 프로젝트가 함께 생긴다 | 도메인 없음 | 만들기 뒤 그 프로젝트를 가진 도메인으로 걸러 조회 | 만든 도메인 |
| 슈퍼관리자가 아닌 사용자가 만들려 한다 | 권한 없음 | 만들기 | 역할로 거부 |
| 집행을 꺼도 슈퍼관리자가 아니면 못 만든다 | 엔티티 권한 집행 꺼짐 | 만들기 | 역할로 거부 |
| 이미 쓰이는 이름으로 만들려 한다 | 그 이름의 도메인이 있음 | 만들기 | 이름이 겹친다는 이유로 거부 |
| 이름이 공백뿐이다 | 도메인 없음 | 만들기 | 입력이 틀렸다는 이유로 거부 |

집행을 끄는 줄이 따로 있는 이유는, 이 문이 권한 그래프가 아니라 역할이라 집행 스위치와
무관하다는 것을 못박기 위해서다.

만들기는 리소스 그룹을 연결하지 않는다. 연결은 리소스 그룹 쪽 허용 목록 호출이 하고, 그
시나리오는 리소스 그룹 어댑터 문서에 있다.

레거시 GQL `CreateDomainNode`·`ModifyDomainNode`는 도메인 만들기·수정과 리소스 그룹 연결을 따로
부른다. 연결이 실패하면 만들기·수정만 반영된 도메인이 남는다.

## 읽기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름으로 읽는다 | 그 이름의 도메인이 있음 | 이름으로 조회 | 그 도메인 |
| 아무 권한도 받지 않은 사용자가 읽는다 | 같은 도메인이 있음 | 이름으로 조회 | 권한 부족으로 거부 |
| 아무 도메인도 갖지 않은 이름으로 읽는다 | 다른 도메인만 있음 | 이름으로 조회 | 대상 없음으로 거부 |
| 슈퍼관리자가 soft delete 된 도메인을 이름으로 읽는다 | 그 도메인이 있음 | soft delete 뒤 이름으로 조회 | 비활성 상태를 실은 그 도메인 |

없는 대상과 권한 없음이 서로 다른 것으로 거부되어야 한다. 하나로 뭉치면 어느 쪽으로 막혔는지
호출자가 알 수 없다.

## 여럿 읽기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 id로 여럿 읽는다 | 그 도메인이 있음 | id 목록으로 조회 | 그 자리에 도메인 |
| 아무 권한도 받지 않은 사용자가 id로 여럿 읽는다 | 같은 도메인이 있음 | id 목록으로 조회 | 그 자리가 권한 부족으로 거부 |

여럿 읽기는 호출 전체를 거부하지 않고 자리마다 답한다.

## 이름으로 id 찾기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름으로 id를 찾는다 | 그 도메인이 있음 | 이름으로 id 찾기 | 그 도메인의 id |
| 아무 권한도 받지 않은 사용자도 이름으로 id를 찾는다 | 같은 도메인이 있음 | 이름으로 id 찾기 | 그 도메인의 id |
| 아무 도메인도 갖지 않은 이름으로 id를 찾는다 | 다른 도메인만 있음 | 이름으로 id 찾기 | 대상 없음으로 거부 |
| 슈퍼관리자가 있는 이름과 없는 이름으로 id를 여럿 찾는다 | 한 이름의 도메인만 있음 | 이름 목록으로 id 찾기 | 있는 이름에는 그 도메인의 id, 없는 이름에는 빈 값 |
| 아무 권한도 받지 않은 사용자가 같은 이름들로 id를 여럿 찾는다 | 같은 도메인이 있음 | 이름 목록으로 id 찾기 | 슈퍼관리자와 같은 답 |
| 로그인 문맥 없이 이름으로 id를 여럿 찾는다 | 그 도메인이 있음 | 이름 목록으로 id 찾기 | 사용자를 찾을 수 없다는 이유로 거부 |

두 호출 모두 인증만 본다. 권한은 그 id를 받는 호출이 본다. 그래서 권한이 없어도 이름이
있는지는 드러나며, 설계상 허용한다. 다른 엔티티의 REST handler와 GQL resolver는 도메인 이름을
id로 풀 때 이 호출을 먼저 부른다. GQL은 여럿 찾기를 이름 → id 로더로 써서 id로 여럿 읽기로
잇는다.

## 수정하기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 설명만 바꾼다 | 그 도메인이 있음 | 설명 수정 | 설명은 새 값, 이름은 그대로 |
| 슈퍼관리자가 활성 플래그를 내린다 | 활성 도메인이 있음 | 활성 플래그 수정 | 비활성 상태를 실은 답 |
| 아무 권한도 받지 않은 사용자가 수정한다 | 같은 도메인이 있음 | 설명 수정 | 권한 부족으로 거부 |
| 아무 도메인도 갖지 않은 이름을 수정한다 | 다른 도메인만 있음 | 설명 수정 | 대상 없음으로 거부 |

수정도 리소스 그룹을 더하거나 빼지 않는다. 만들기와 같이 리소스 그룹 쪽 허용 목록 호출이 한다.

## soft delete, restore, purge

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 soft delete 한다 | 그 도메인이 있음 | soft delete | soft delete 했다는 답 |
| 이미 soft delete 된 것을 다시 soft delete 한다 | 그 도메인이 있음 | soft delete 두 번 | 두 번째도 soft delete 했다는 답 |
| 아무 권한도 받지 않은 사용자가 soft delete 한다 | 같은 도메인이 있음 | soft delete | 권한 부족으로 거부 |
| 아무 도메인도 갖지 않은 이름을 soft delete 한다 | 다른 도메인만 있음 | soft delete | 대상 없음으로 거부 |
| soft delete 된 것을 restore 한다 | 그 도메인이 있음 | soft delete 뒤 restore | restore 했다는 답 |
| soft delete 되지 않은 것을 restore 한다 | 활성 도메인이 있음 | restore | restore 했다는 답 |
| 아무 권한도 받지 않은 사용자가 restore 한다 | 같은 도메인이 있음 | restore | 권한 부족으로 거부 |
| 아무것도 딸려 있지 않은 것을 purge 한다 | 참조 없는 활성 도메인이 있음 | purge | purge 했다는 답 |
| 아무 권한도 받지 않은 사용자가 purge 한다 | 참조 없는 도메인이 있음 | purge | 권한 부족으로 거부 |
| 프로젝트가 딸린 것을 purge 한다 | 프로젝트 하나가 딸린 도메인이 있음 | purge | 프로젝트가 남아 있다는 이유로 거부 |
| 사용자가 딸린 것을 purge 한다 | 사용자 한 명이 딸린 도메인이 있음 | purge | 사용자가 남아 있다는 이유로 거부 |
| 아무 도메인도 갖지 않은 이름을 purge 한다 | 다른 도메인만 있음 | purge | 대상 없음으로 거부 |

soft delete 와 restore 는 지금 상태를 보지 않는다. 이미 그 상태여도 했다는 답이 온다. purge 도
soft delete 되었는지를 보지 않는다. 딸린 것이 없으면 활성 도메인도 purge 된다.

soft delete 는 활성 플래그를 내리고 상태를 삭제로 바꾼다. 수정으로 활성 플래그만 내린 도메인은
비활성일 뿐 soft delete 된 것이 아니다.

## search

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 필터 없이 search 한다 | 도메인 넷을 미리 만듦 | 전체 search | 넷이 모두 나옴 |
| soft delete 된 것이 섞여도 필터 없이 search 한다 | 도메인 넷 | 하나를 soft delete 한 뒤 전체 search | soft delete 된 것까지 넷이 모두 나옴 |
| 이름으로 걸러 search 한다 | 도메인 여럿이 있음 | 이름 필터 search | 그 이름의 것만 남음 |
| 슈퍼관리자가 아닌 사용자가 전체를 search 한다 | 권한 없음 | 전체 search | 역할로 거부 |

## 리소스 그룹 범위에서 search

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 리소스 그룹 범위에서 search 한다 | 그 그룹을 쓸 수 있는 도메인 둘과 쓸 수 없는 하나 | 그 그룹 범위 search | 쓸 수 있는 둘만 남음 |
| 그 범위에서 도메인 읽기 역할을 받은 사용자가 search 한다 | 같은 도메인들 | 그 그룹 범위 search | 슈퍼관리자와 같은 둘 |
| 아무 권한도 받지 않은 사용자가 search 한다 | 같은 도메인들 | 그 그룹 범위 search | 권한 부족으로 거부 |

리소스 그룹 이름으로 묻는 GQL resolver는 리소스 그룹 adapter의 이름으로 id 찾기를 먼저 부르고,
얻은 id를 범위로 넘긴다. 도메인 adapter는 리소스 그룹 이름을 풀지 않는다.

## 아직 적지 않은 것

어느 시나리오도 부르지 않는 어댑터 호출이다. 실행 결과가 이 목록을 함께 낸다.

`batch_load_fields` — 공통 베이스가 내놓는 호출이라 도메인 시나리오가 부르지 않는다.

적지 않은 행과 그 이유.

| 행 | 이유 |
|---|---|
| 실행 중인 kernel 이 딸린 것을 purge 한다 | adapter 기반 시나리오로는 kernel 이 실행 중인 상태를 보장할 수 없다. agent 에 닿는 동작은 이 시나리오의 범위 밖이다 |
