# 런타임 변형 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 어긋나면 문장 쪽을 먼저
의심한다.

런타임 변형은 어느 스코프에도 속하지 않게 만들어진다. 생성은 전역 역할이 있어야 하고, 하나를
지정해 수정·삭제하는 호출은 그 변형에 부여된 권한을 검사한다. 그런데 역할은 스코프에 속하고
이 변형은 어느 스코프에도 없으므로, 그 권한을 받을 방법이 없다. 두 경로 모두 슈퍼관리자만
통과하지만 거부 이유가 서로 다르고, 권한 검사 스위치에는 뒤의 경로만 반응한다. 조회 셋은 어떤
검사도 없이 인증만 확인한다.

변형 아래 놓이는 preset은 자기 어댑터를 가지므로 `../runtime_variant_preset/KNOWLEDGE.md`에
있다.

## 생성

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름만 지정해 생성한다 | 변형 없음, 전역 역할 있음 | 이름만 지정해 생성 | 설명은 비고, 폴더 설정 파일은 읽지 않으며, 모델 정의는 코드가 정해 둔 기본값인 노드 |
| 이름과 설명을 함께 지정해 생성한다 | 변형 없음, 전역 역할 있음 | 이름과 설명으로 생성 | 지정한 값이 그대로 담긴 노드 |
| 이미 사용 중인 이름으로 생성한다 | 그 이름의 변형이 있음, 전역 역할 있음 | 생성 | 이름 중복으로 거부 |
| 슈퍼관리자가 아닌 사용자가 생성한다 | 전역 역할 없음 | 생성 | 역할 부족으로 거부 |
| 권한 검사를 꺼도 슈퍼관리자가 아니면 생성할 수 없다 | 권한 검사 비활성화, 전역 역할 없음 | 생성 | 역할 부족으로 거부 |

모델 정의와 폴더 설정 파일 플래그는 요청으로 정할 수 없다. 생성이 값을 고정하고, 어느 호출도
그 둘을 바꾸지 않는다. 생성 시점의 값이 그 변형의 평생 값이므로 첫 시나리오가 둘을 함께
검사한다.

이름이 비어 있거나 길이 제한을 넘는 요청은 시나리오로 두지 않는다. 요청 타입이 이미 막으므로
어댑터가 보장하는 것이 아니다.

권한 검사를 끄는 시나리오는 생성이 역할로 보호되어 스위치가 영향을 주지 않는다는 것을
고정한다. 수정과 삭제 절의 같은 시나리오와 결과가 반대인 곳이다.

## 조회

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 아무 권한도 없는 사용자가 id로 조회한다 | 변형 하나, 아무 권한도 없음 | id로 조회 | 그 변형 전체 |
| 존재하지 않는 id로 조회한다 | 다른 변형만 있음 | id로 조회 | 대상을 찾을 수 없어 거부 |
| 이름으로 id를 얻는다 | 변형 하나, 아무 권한도 없음 | 이름을 id로 변환 | 그 변형의 id |
| 존재하지 않는 이름을 변환한다 | 다른 변형만 있음 | 이름을 id로 변환 | 대상을 찾을 수 없어 거부 |
| 있는 것과 없는 것을 섞어 조회한다 | 변형 둘, 아무 권한도 없음 | 세 id를 한 번에 | 목록 순서대로, 없는 id 자리는 비어서 반환된다 |
| 빈 목록을 준다 | 변형 하나 | 빈 id 목록 | 빈 응답. 하위 계층을 호출하지 않는다 |

조회에는 권한 검사가 없다. 아무 권한도 없는 사용자가 성공하는 시나리오가 그것을 증명하므로, 이
절에는 권한 부족으로 거부되는 짝이 없다. 짝은 생성 절의 역할 부족으로 거부되는 시나리오다 —
같은 사용자가 조회할 수는 있고 생성할 수는 없다.

이름을 id로 변환하는 호출에는 뒤따르는 권한 검사가 없다. 그래서 존재하지 않는 이름이 "대상
없음"으로 그대로 드러난다. 권한 검사가 뒤따르는 변환은 존재하지 않는 키와 접근할 수 없는 키를
같은 이유로 거부하는데, 이 변환은 그쪽이 아니다.

인증되지 않은 호출은 시나리오로 두지 않는다. 시나리오는 언제나 미리 만들어 둔 사용자로 호출한다.

## 수정

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름만 바꾼다 | 설명이 있는 변형 하나, 전역 역할 있음 | 이름 수정 | 이름은 새 값, 설명은 그대로 |
| 설명을 지운다 | 설명이 있는 변형, 전역 역할 있음 | 설명을 비우는 수정 | 설명이 없어진다 |
| 값을 하나도 지정하지 않는다 | 변형 하나, 전역 역할 있음 | 빈 수정 | 아무것도 바뀌지 않은 노드 |
| 이미 사용 중인 이름으로 바꾼다 | 변형 둘, 전역 역할 있음 | 한쪽 이름을 다른 쪽 이름으로 수정 | 이름 중복으로 거부 |
| 존재하지 않는 id를 수정한다 | 다른 변형만 있음, 전역 역할 있음 | 이름 수정 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 수정한다 | 같은 변형, 아무 권한도 없음 | 이름 수정 | 권한 부족으로 거부 |
| 아무 권한도 없는 사용자가 없는 id를 수정한다 | 다른 변형만 있음, 아무 권한도 없음 | 이름 수정 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 수정된다 | 권한 검사 비활성화, 아무 권한도 없음 | 이름 수정 | 이름이 새 값인 노드 |

설명은 세 가지(생략·비우기·값 지정)를 받고 이름은 생략과 값 지정 둘뿐이다. 그래서 비우는
시나리오는 설명에만 둔다.

존재하지 않는 id는 슈퍼관리자와 그 밖의 사용자에게 서로 다른 이유로 거부된다. 권한 검사가 먼저
실행되는데 없는 행에는 부여된 권한도 없으므로, 그 검사를 통과하는 슈퍼관리자만 "대상 없음"을
본다. 삭제 절의 같은 시나리오도 마찬가지다.

이름 중복 거부는 생성할 때와 수정할 때 서로 다른 오류로 온다. 생성은 이 엔티티의 오류로
거부하고, 수정은 저장소의 제약 위반을 그대로 전파한다. 시나리오를 적기 전에 하나로 맞출 것인지
정한다.

마지막 시나리오가 이 어댑터에서 가장 중요하다. 권한 검사를 끄면 아무 권한도 없는 사용자가 전역
카탈로그의 행을 수정할 수 있는데, 같은 스위치로 생성은 허용되지 않는다. 두 경로가 서로 다른
것을 검사하기 때문이고, 그것이 의도인지는 이 시나리오를 실행해 본 뒤 정한다.

## 삭제

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 삭제한다 | 변형 하나, 전역 역할 있음 | 삭제 | 삭제한 id를 담은 응답 |
| 존재하지 않는 id를 삭제한다 | 다른 변형만 있음, 전역 역할 있음 | 삭제 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 삭제한다 | 같은 변형, 아무 권한도 없음 | 삭제 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 삭제된다 | 권한 검사 비활성화, 아무 권한도 없음 | 삭제 | 삭제한 id를 담은 응답 |
| 여럿을 한 번에 삭제한다 | 변형 둘, 전역 역할 있음 | 두 id를 한 번에 | 요청한 id의 수를 담은 응답 |
| 없는 id가 섞인 목록을 삭제한다 | 변형 하나, 전역 역할 있음 | 있는 id 뒤에 없는 id를 붙여 한 번에 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 여럿을 삭제한다 | 변형 둘, 아무 권한도 없음 | 두 id를 한 번에 | 권한 부족으로 거부 |

일괄 삭제는 단건 삭제를 id마다 반복하는 것이다. 한 트랜잭션이 아니어서 중간에 거부되면 앞의
것은 삭제된 채 남는다. 여섯 번째 시나리오의 거부가 그 경우이고, 남은 것은 응답에 담기지
않으므로 시나리오는 거부만 확인한다. 응답의 수는 삭제한 수가 아니라 요청한 id의 수인데, 끝까지
성공했을 때만 응답이 오므로 둘이 같다.

preset이 딸린 변형을 삭제하는 시나리오는 아직 두지 않는다. preset의 변형 컬럼에 외래 키가
선언된 곳과 선언되지 않은 곳이 갈려 있어, 마이그레이션으로 만든 데이터베이스에서는 preset이
함께 사라지고 스키마를 한 번에 만든 데이터베이스에서는 남는다. 어느 쪽이 맞는지 정한 뒤
시나리오를 적는다.

이 어댑터에는 soft delete가 없다. 삭제하면 행이 사라지고 되살리는 호출도 없다.

## 아직 적지 않은 것

없다. 어댑터가 제공하는 여덟 호출이 모두 위에 있다.

`batch_load_fields`는 모든 어댑터가 물려받는 공용 도우미이지 이 엔티티의 호출이 아니다. 레포트가
함께 세지만 적을 것이 없다.
