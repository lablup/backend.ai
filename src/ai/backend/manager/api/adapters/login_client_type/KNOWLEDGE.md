# 로그인 클라이언트 종류 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 어긋나면 문장 쪽을 먼저
의심한다.

로그인 클라이언트 종류는 어느 스코프에도 속하지 않게 만들어진다. 생성은 전역 역할이 있어야 하고,
하나를 지정해 수정·삭제하는 호출은 그 종류에 부여된 권한을 검사하는데 그 권한을 받을 방법이
없다. 두 경로 모두 슈퍼관리자만 통과하지만 거부 이유가 서로 다르고, 권한 검사 스위치에는 뒤의
경로만 반응한다. 조회와 검색은 인증만 확인한다.

## 생성

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름만 지정해 생성한다 | 종류 없음, 전역 역할 있음 | 이름만 지정해 생성 | 설명이 비어 있는 노드 |
| 이름과 설명을 함께 지정해 생성한다 | 종류 없음, 전역 역할 있음 | 이름과 설명으로 생성 | 지정한 값이 그대로 담긴 노드 |
| 이미 사용 중인 이름으로 생성한다 | 그 이름의 종류가 있음, 전역 역할 있음 | 생성 | 이름 중복으로 거부 |
| 슈퍼관리자가 아닌 사용자가 생성한다 | 전역 역할 없음 | 생성 | 역할 부족으로 거부 |
| 권한 검사를 꺼도 슈퍼관리자가 아니면 생성할 수 없다 | 권한 검사 비활성화, 전역 역할 없음 | 생성 | 역할 부족으로 거부 |

이름이 비어 있거나 길이 제한을 넘는 요청은 시나리오로 두지 않는다. 요청 타입이 이미 막기
때문이다.

## 조회

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 아무 권한도 없는 사용자가 id로 조회한다 | 종류 하나, 아무 권한도 없음 | id로 조회 | 그 종류 전체 |
| 존재하지 않는 id로 조회한다 | 다른 종류만 있음 | id로 조회 | 대상을 찾을 수 없어 거부 |

조회에는 권한 검사가 없다. 아무 권한도 없는 사용자가 성공하는 시나리오가 그것을 증명하므로 이
절에는 거부 짝이 없고, 짝은 생성 절의 역할 부족으로 거부되는 시나리오다.

인증되지 않은 호출은 시나리오로 두지 않는다. 시나리오는 언제나 미리 만들어 둔 사용자로 호출한다.

## 검색

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 아무 권한도 없는 사용자가 검색한다 | 종류 둘, 아무 권한도 없음 | 전체 조회 | 둘 다 집계된다 |
| 이름 필터로 검색한다 | 이름이 다른 종류 여럿 | 이름 필터 조회 | 그 이름의 종류만 남는다 |
| 페이지 크기를 생략한다 | 종류 51개 | 크기 없이 조회 | 50건까지 반환되고 다음 페이지가 있다고 응답한다 |

기본 페이지 크기가 다른 카탈로그의 10이 아니라 50이다. 세 번째 시나리오가 그 수를 고정한다.

요청 타입이 커서를 받지만 이 검색은 크기와 건너뛸 수만 읽는다. 커서를 함께 주면 지금은 조용히
무시된다. 시나리오를 적기 전에 무시할 것인지 사용할 것인지 정한다.

## 수정

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이름만 바꾼다 | 설명이 있는 종류 하나, 전역 역할 있음 | 이름 수정 | 이름은 새 값, 설명은 그대로 |
| 설명을 지운다 | 설명이 있는 종류, 전역 역할 있음 | 설명을 비우는 수정 | 설명이 없어진다 |
| 값을 하나도 지정하지 않는다 | 종류 하나, 전역 역할 있음 | 빈 수정 | 아무것도 바뀌지 않은 노드 |
| 이미 사용 중인 이름으로 바꾼다 | 종류 둘, 전역 역할 있음 | 한쪽 이름을 다른 쪽 이름으로 수정 | 이름 중복으로 거부 |
| 존재하지 않는 id를 수정한다 | 다른 종류만 있음, 전역 역할 있음 | 이름 수정 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 수정한다 | 같은 종류, 아무 권한도 없음 | 이름 수정 | 권한 부족으로 거부 |
| 아무 권한도 없는 사용자가 없는 id를 수정한다 | 다른 종류만 있음, 아무 권한도 없음 | 이름 수정 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 수정된다 | 권한 검사 비활성화, 아무 권한도 없음 | 이름 수정 | 이름이 새 값인 노드 |

수정은 대상 id를 요청 본문 밖에서 따로 받는다. 시나리오가 id를 두 곳에 적지 않도록 이 구조를
유지한다.

존재하지 않는 id는 슈퍼관리자와 그 밖의 사용자에게 서로 다른 이유로 거부된다. 권한 검사가 먼저
실행되는데 없는 행에는 부여된 권한도 없으므로, 그 검사를 통과하는 슈퍼관리자만 "대상 없음"을
본다. 삭제 절의 같은 시나리오도 마찬가지다.

이름 중복 거부는 생성할 때와 수정할 때 서로 다른 오류로 온다. 생성은 이 엔티티의 오류로
거부하고, 수정은 저장소의 제약 위반을 그대로 전파한다. 시나리오를 적기 전에 하나로 맞출 것인지
정한다.

## 삭제

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 삭제한다 | 종류 하나, 전역 역할 있음 | 삭제 | 삭제한 id를 담은 응답 |
| 존재하지 않는 id를 삭제한다 | 다른 종류만 있음, 전역 역할 있음 | 삭제 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 삭제한다 | 같은 종류, 아무 권한도 없음 | 삭제 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 삭제된다 | 권한 검사 비활성화, 아무 권한도 없음 | 삭제 | 삭제한 id를 담은 응답 |

권한 검사를 끄는 시나리오들이 생성 절과 반대 결과를 갖는다. 수정과 삭제는 역할이 아니라 권한
그래프로 보호되므로 스위치가 영향을 준다. 같은 스위치로 아무 권한 없는 사용자가 종류를 수정하고
삭제할 수 있게 되지만 생성할 수는 없다. 그것이 의도인지는 이 시나리오들을 실행해 본 뒤 정한다.

이 어댑터에는 soft delete가 없다.

## 아직 적지 않은 것

함께 세지만 적을 것이 없다.
