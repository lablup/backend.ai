# 컨테이너 레지스트리 어댑터 — 시나리오

이 패키지는 컨테이너 레지스트리 API 요청을 레지스트리 및 RBAC 프로세서 호출로 변환한다. 아래
시나리오는 어댑터가 보장하는 권한 검사, 반환값, 오류를 정리한다.

## 대부분의 호출은 슈퍼관리자만 실행할 수 있다

- 컨테이너 레지스트리는 특정 스코프에 속하지 않으며, 개별 레지스트리를 RBAC 엔티티로 조회하는
  구성도 없다.
- 허용 프로젝트를 변경하는 호출을 제외하면 RBAC 권한이 아니라 슈퍼관리자 여부로 접근을
  제어한다.
- 허용 프로젝트 추가와 제거는 RBAC 관계 작업을 사용하므로 레지스트리와 프로젝트 양쪽의 권한을
  검사하며, 엔티티 권한 검사 설정의 영향을 받는다.
- 레지스트리가 소유한 이미지는 [이미지 어댑터](../image/KNOWLEDGE.md)가 처리한다. 이미지
  리스캔은 REST v1 핸들러가 프로세서를 직접 호출하므로 이 어댑터의 보장 범위에 포함되지 않는다.

## 생성 시 기본값과 허용 프로젝트 관계를 함께 처리한다

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 필수 값만 지정해 생성한다 | 레지스트리가 없고 호출자가 슈퍼관리자임 | 주소·이름·종류를 지정해 생성 | 프로젝트·계정·추가 설정은 비어 있고, SSL 검증과 전역 설정은 활성화된 레지스트리 |
| 허용 프로젝트를 지정해 생성한다 | 프로젝트가 있고 호출자가 슈퍼관리자임 | 허용 프로젝트를 지정해 생성 | 레지스트리와 프로젝트 사이의 관계도 함께 생성됨 |
| 존재하지 않는 프로젝트를 지정해 생성한다 | 프로젝트가 없고 호출자가 슈퍼관리자임 | 허용 프로젝트를 지정해 생성 | 프로젝트를 찾을 수 없다는 오류 |
| 일반 사용자가 생성한다 | 호출자가 슈퍼관리자가 아님 | 생성 | 슈퍼관리자 전용 작업이라는 오류 |
| 엔티티 권한 검사를 비활성화한 뒤 일반 사용자가 생성한다 | 엔티티 권한 검사가 비활성화되어 있고 호출자가 슈퍼관리자가 아님 | 생성 | 슈퍼관리자 전용 작업이라는 오류 |

- 주소나 이름이 공백으로만 이루어진 요청은 요청 타입에서 거부하므로 어댑터 시나리오에 포함하지
  않는다.
- SSL 검증과 전역 설정을 생략해도 두 설정은 활성화된다.
- 엔티티 권한 검사 설정은 RBAC 검사에만 적용되므로 슈퍼관리자 여부를 확인하는 생성 작업에는
  영향을 주지 않는다.
- 허용 프로젝트를 포함한 생성도 슈퍼관리자 전용이며, 새 레지스트리에 대한 권한을 미리 부여할
  필요는 없다.

## 검색은 필터와 두 가지 페이지네이션 방식을 지원한다

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 필터 없이 검색한다 | 레지스트리가 두 개 있고 호출자가 슈퍼관리자임 | 전체 검색 | 두 레지스트리와 총 개수 2 |
| 이름으로 필터링한다 | 이름이 서로 다른 레지스트리가 여러 개 있고 호출자가 슈퍼관리자임 | 이름 필터로 검색 | 조건에 맞는 레지스트리만 반환됨 |
| 유형으로 필터링한다 | 유형이 서로 다른 레지스트리가 있고 호출자가 슈퍼관리자임 | Docker 유형으로 검색 | Docker 레지스트리만 반환됨 |
| 전역 여부로 필터링한다 | 전역 여부가 서로 다른 레지스트리가 있고 호출자가 슈퍼관리자임 | 전역이 아닌 레지스트리 검색 | 전역이 아닌 레지스트리만 반환됨 |
| `AND`로 필터를 결합한다 | 유형과 전역 여부가 서로 다른 레지스트리가 있음 | Docker 유형이면서 전역인 레지스트리 검색 | 두 조건을 모두 만족하는 레지스트리만 반환됨 |
| `OR`로 필터를 결합한다 | 유형과 전역 여부가 서로 다른 레지스트리가 있음 | Docker 유형이거나 전역이 아닌 레지스트리 검색 | 한 조건 이상을 만족하는 레지스트리가 반환됨 |
| `NOT`으로 필터를 반전한다 | 전역 여부가 서로 다른 레지스트리가 있음 | 전역이 아닌 조건을 반전해 검색 | 전역 레지스트리만 반환됨 |
| 페이지 크기를 생략한다 | 레지스트리가 열한 개 있고 호출자가 슈퍼관리자임 | 페이지 크기 없이 검색 | 최대 열 개를 반환하고 다음 페이지가 있음을 표시함 |
| 이름으로 정렬한다 | 이름이 서로 다른 레지스트리가 세 개 있음 | 이름 오름차순 검색 | 이름 오름차순으로 반환됨 |
| 오프셋으로 중간 페이지를 조회한다 | 레지스트리가 세 개 있음 | 한 건을 건너뛰고 한 건 조회 | 가운데 레지스트리와 이전·다음 페이지 표시가 반환됨 |
| 오프셋이 끝을 지난다 | 레지스트리가 세 개 있음 | 세 건을 건너뛰고 한 건 조회 | 빈 목록과 이전 페이지 표시가 반환됨 |
| 정방향 커서로 다음 페이지를 조회한다 | 레지스트리가 세 개 있음 | 첫 레지스트리 뒤에서 한 건 조회 | 다음 레지스트리와 이전·다음 페이지 표시가 반환됨 |
| 역방향 커서로 이전 페이지를 조회한다 | 레지스트리가 세 개 있음 | 마지막 레지스트리 앞에서 한 건 조회 | 이전 레지스트리와 이전·다음 페이지 표시가 반환됨 |
| 페이지네이션 방식을 함께 지정한다 | 레지스트리가 있음 | 커서와 오프셋 페이지네이션을 함께 지정 | 잘못된 인자라는 오류 |
| 일반 사용자가 검색한다 | 호출자가 슈퍼관리자가 아님 | 전체 검색 | 슈퍼관리자 전용 작업이라는 오류 |

- 검색은 커서 기반 페이지네이션과 크기·오프셋 기반 페이지네이션을 모두 지원한다.
- 두 페이지네이션 방식을 한 요청에 함께 지정하면 잘못된 인자라는 오류가 발생한다.
- 커서 값은 기본 ID 정렬을 기준으로 하며, 정방향은 내림차순, 역방향은 오름차순으로 다음 행을 찾는다.

## 여러 ID를 요청 순서대로 조회한다

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 존재하는 ID와 존재하지 않는 ID를 함께 조회한다 | 레지스트리가 두 개 있고 호출자가 슈퍼관리자임 | 세 ID를 한 번에 조회 | 요청 순서를 유지하고 존재하지 않는 ID 위치에는 빈 값이 반환됨 |
| 빈 ID 목록을 조회한다 | 레지스트리가 하나 있고 호출자가 슈퍼관리자임 | 빈 ID 목록 조회 | 실제 조회를 실행하지 않고 빈 목록을 반환함 |
| 일반 사용자가 여러 ID를 조회한다 | 호출자가 슈퍼관리자가 아님 | 두 ID를 한 번에 조회 | 요청 전체가 슈퍼관리자 전용 작업이라는 오류로 거부됨 |

여러 ID를 조회하는 호출은 내부적으로 전역 조회를 한 번 실행한다. 따라서 호출자에게 권한이 없으면
ID별로 결과를 나누지 않고 요청 전체를 거부한다.

## 수정 후 레지스트리 주소와 유형을 검증한다

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 주소만 수정한다 | 레지스트리가 있고 호출자가 슈퍼관리자임 | 주소 수정 | 주소만 바뀌고 나머지 값은 유지됨 |
| 수정할 값을 지정하지 않는다 | 레지스트리가 있고 호출자가 슈퍼관리자임 | 빈 수정 요청 | 값이 바뀌지 않은 레지스트리 |
| 허용 프로젝트를 지정해 수정한다 | 레지스트리와 프로젝트가 있고 호출자가 슈퍼관리자임 | 허용 프로젝트 추가와 수정 | 레지스트리 값은 유지되고 프로젝트 관계가 생성됨 |
| 호스트가 없는 주소로 수정한다 | 레지스트리가 있고 호출자가 슈퍼관리자임 | 주소 수정 | 잘못된 주소 형식이라는 오류 |
| Harbor 레지스트리의 프로젝트 값을 비운다 | Harbor 레지스트리가 있고 호출자가 슈퍼관리자임 | 프로젝트 수정 | Harbor 레지스트리에는 프로젝트 값이 필요하다는 오류 |
| 존재하지 않는 ID를 수정한다 | 다른 레지스트리만 있고 호출자가 슈퍼관리자임 | 주소 수정 | 레지스트리를 찾을 수 없다는 오류 |
| 일반 사용자가 수정한다 | 레지스트리가 있고 호출자가 슈퍼관리자가 아님 | 주소 수정 | 슈퍼관리자 전용 작업이라는 오류 |

- 주소 검증은 호스트의 존재 여부만 확인하며 스킴은 제한하지 않는다.
- `http` 또는 `https`로 시작하지 않는 주소에는 `http://`를 붙인 뒤 파싱한다. 따라서
  `ftp://reg.example`이나 공백이 포함된 문자열도 통과하며, 호스트가 비어 있는 주소만 거부된다.
- 이 검증 범위를 강화할지는 아직 결정되지 않았다.
- 검증은 수정 후의 최종 값을 대상으로 한다. 요청에서 주소나 프로젝트를 생략하더라도 저장된 값이
  규칙을 위반하면 수정 요청을 거부한다.

## 허용 프로젝트 변경은 두 스코프의 권한을 검사한다

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 양쪽 스코프에 권한이 있는 사용자가 프로젝트를 추가한다 | 레지스트리와 프로젝트 양쪽에 권한이 있음 | 허용 프로젝트 추가 | 관계가 생성됨 |
| 이미 허용된 프로젝트를 다시 추가한다 | 관계가 이미 있고 양쪽 스코프에 권한이 있음 | 허용 프로젝트 추가 | 기존 관계를 유지하며 중복을 생성하지 않음 |
| 생성 권한만 있는 사용자가 프로젝트를 추가한다 | 양쪽 스코프에 생성 권한만 있음 | 허용 프로젝트 추가 | 관계가 생성됨 |
| 삭제 권한만 있는 사용자가 프로젝트를 추가한다 | 양쪽 스코프에 삭제 권한만 있음 | 허용 프로젝트 추가 | 권한 부족 오류 |
| 허용된 프로젝트를 제거한다 | 관계가 있고 양쪽 스코프에 권한이 있음 | 허용 프로젝트 제거 | 관계가 삭제됨 |
| 삭제 권한만 있는 사용자가 프로젝트를 제거한다 | 관계가 있고 양쪽 스코프에 삭제 권한만 있음 | 허용 프로젝트 제거 | 관계가 삭제됨 |
| 생성 권한만 있는 사용자가 프로젝트를 제거한다 | 관계가 있고 양쪽 스코프에 생성 권한만 있음 | 허용 프로젝트 제거 | 권한 부족 오류이고 관계가 유지됨 |
| 존재하지 않는 프로젝트를 추가한다 | 프로젝트가 없고 호출자가 슈퍼관리자임 | 허용 프로젝트 추가 | 프로젝트를 찾을 수 없다는 오류 |
| 허용되지 않은 프로젝트만 제거한다 | 프로젝트가 레지스트리에 연결되어 있지 않고 호출자가 슈퍼관리자임 | 허용 프로젝트 제거 | 관계를 찾을 수 없다는 오류 |
| 프로젝트 권한이 없는 사용자가 프로젝트를 추가한다 | 레지스트리에만 권한이 있음 | 허용 프로젝트 추가 | 권한 부족 오류 |
| 레지스트리 권한이 없는 사용자가 프로젝트를 추가한다 | 프로젝트에만 권한이 있음 | 허용 프로젝트 추가 | 권한 부족 오류 |
| 엔티티 권한 검사를 비활성화한 뒤 권한이 없는 사용자가 프로젝트를 추가한다 | 엔티티 권한 검사가 비활성화되어 있고 양쪽 스코프 모두에 권한이 없음 | 허용 프로젝트 추가 | 관계가 생성됨 |

- 관계 작업은 레지스트리와 프로젝트를 한 쌍으로 권한 검사하며, 둘 중 하나라도 허용되지 않으면
  요청 전체를 거부한다.
- 일반 사용자는 관계 상태를 확인하기 전에 권한 검사에서 거부된다. 따라서 존재하지 않는 프로젝트와
  연결되지 않은 관계에 대한 오류 시나리오는 슈퍼관리자로 실행한다.
- 엔티티 권한 검사를 비활성화하면 권한이 없는 사용자도 관계를 변경할 수 있다. 슈퍼관리자 여부를
  직접 확인하는 생성 작업과 다른 결과가 나오는 이유다.
- 이미 존재하는 관계를 다시 추가하는 작업은 멱등하다. 제거 요청에 포함된 관계가 하나도 삭제되지
  않았을 때만 오류가 발생한다.
- 추가는 양쪽 스코프의 생성 권한을, 제거는 양쪽 스코프의 삭제 권한을 요구한다. 다른 동작의 권한은
  대신 사용할 수 없다.
- 관계 변경 시나리오는 호출 결과뿐 아니라 연관 테이블의 행 수를 확인하여 생성·유지·삭제 여부와
  거부된 요청에 부수효과가 없음을 검증한다.

## 삭제는 레지스트리와 허용 프로젝트 관계를 함께 제거한다

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 레지스트리를 삭제한다 | 레지스트리가 있고 호출자가 슈퍼관리자임 | 삭제 | 삭제한 레지스트리의 ID |
| 허용 프로젝트가 연결된 레지스트리를 삭제한다 | 프로젝트 관계가 있는 레지스트리가 있고 호출자가 슈퍼관리자임 | 삭제 | 레지스트리와 프로젝트 관계가 함께 삭제됨 |
| 존재하지 않는 ID를 삭제한다 | 다른 레지스트리만 있고 호출자가 슈퍼관리자임 | 삭제 | 레지스트리를 찾을 수 없다는 오류 |
| 일반 사용자가 삭제한다 | 레지스트리가 있고 호출자가 슈퍼관리자가 아님 | 삭제 | 슈퍼관리자 전용 작업이라는 오류 |

이 어댑터는 논리 삭제와 복원을 지원하지 않는다. 삭제하면 레지스트리 행이 데이터베이스에서
제거된다.

## 필드 일괄 조회는 아직 시나리오로 검증하지 않는다

- 어댑터가 직접 정의한 여섯 호출은 모두 위 시나리오에서 다룬다.
- `batch_load_fields`는 공통 어댑터에서 상속한 필드 일괄 조회 호출이며, 아직 사용하는
  시나리오가 없다. 레지스트리에서 일괄 조회할 필드가 정해지면 시나리오를 추가한다.
- 허용 프로젝트 변경 호출은 반환값이 없고 생성·수정·삭제 응답에도 프로젝트 관계가 포함되지
  않으므로, 해당 시나리오는 어댑터 호출 뒤 연관 테이블을 조회해 최종 상태를 검증한다.
