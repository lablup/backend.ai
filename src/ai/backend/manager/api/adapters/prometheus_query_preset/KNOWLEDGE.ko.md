# prometheus_query_preset adapter: 배경

규칙은 상위 디렉터리의 `AGENTS.md` 에 있다. 이 문서와 실행 결과가 어긋나면 문장을 먼저 의심한다.

`prometheus_query_preset`(이하 프리셋)은 지표를 읽는 질의 템플릿을 저장한다. row 는 global 과 public 양쪽에 속한다. 저장된 프리셋을 조회하고 검색하는 것은 public 에서 READ 를 검사한다. 모든 계정이 public 소속 역할을 자동으로 받으므로 로그인한 사용자는 모두 볼 수 있다. 생성과 미리 보기는 superadmin 인지 검사한다. 수정과 삭제에 필요한 권한은 global 에서만 나오므로 superadmin 만 통과한다. 실행은 조회와 같은 권한을 요구한다. 저장된 프리셋을 보는 경로와 그 프리셋으로 Prometheus 에 질의하는 경로가 다르다는 것이 이 adapter 의 요지다. 프리셋을 스코프에 공유하는 시나리오는 이 문서에 없다. 공유 adapter 문서에 둔다.

실행과 미리 보기는 응답을 Prometheus 에서 받아 온다. 실행과 미리 보기 절의 시나리오는 mock Prometheus 를 실행해 둔 상태로 실행한다. mock 서버는 모든 질의에 샘플 하나를 응답하고, 그 샘플 값에 받은 질의를 그대로 넣는다. 시나리오는 그 값에서 `time_window` 값이 질의에 어떻게 반영되었는지 확인한다. range query 에는 range query 의 응답 형식으로, instant query 에는 instant query 의 응답 형식으로 응답하고, 빈 질의는 실제 Prometheus 처럼 거부한다. 생성, 조회, 검색, 여러 id 조회, 수정, 삭제, 여럿 수정, 여럿 삭제는 데이터베이스만으로 실행된다.

컨테이너 지표 자체를 읽는 경로인 전체 지표 검색, 지표 이름 목록, 한 사용자의 지표 조회는 adapter 가 없고 legacy GraphQL 이 processor 를 직접 호출하므로 이 문서에 없다.

## 생성

저장하기 전에 렌더러가 템플릿을 검사하고, 거부되면 row 는 생기지 않는다. 그 검사는 시나리오로 두지 않는다. adapter 와 데이터베이스가 결과를 변경하지 않고, 렌더러의 단위 테스트가 거부 사례를 모두 다루고, service 의 단위 테스트는 거부된 템플릿이 저장되지 않는다는 것을 검사한다. 수정과 미리 보기의 템플릿 검사도 같다.

프리셋의 이름에는 유일 제약이 없다. "같은 이름으로 다시 생성한다"가 그것을 확인한다. 카테고리의 이름과 반대다.

존재하지 않는 카테고리는 저장소의 참조 제약이 거부하며 도메인 에러로 변환되지 않는다. 수정의 같은 시나리오도 마찬가지다.

이름이 공백뿐인 요청, `rank` 값이 음수인 요청, `time_window` 값의 형식이 잘못된 요청은 시나리오로 두지 않는다. 요청 타입이 이미 거부하므로 adapter 가 보장하는 동작이 아니다.

"monitor 역할 사용자가 생성한다"는 superadmin 검사가 읽기에만 monitor 를 허용한다는 것을 확인한다. 미리 보기 절의 "monitor 역할 사용자가 미리 본다"와 결과가 반대다.

## 조회

조회는 public 에서 READ 를 검사한다. "public 에서 읽는 사용자가 조회한다"의 요청 사용자가 그 권한만 받은 사용자인 이유다. 권한 검사가 먼저 실행되고 없는 row 에는 부여된 권한도 없으므로, 존재하지 않는 id 와 접근할 수 없는 id 는 같은 이유로 거부된다.

## 여러 id 로 조회

검색을 id 조건으로 호출하는 것이라 권한 경로가 검색과 같다. 스코프가 응답한 row 만 반환되므로 없는 id 는 빈 항목이 된다.

## 수정

`filter_labels` 값과 `group_labels` 값은 `options` column 하나에 함께 저장된다. 하나만 수정해도 다른 하나가 삭제되지 않는다는 것을 시나리오로 둔다.

템플릿 검사는 요청이 템플릿을 지정했을 때만 하고 저장된 템플릿은 다시 검사하지 않는다. 이것도 service 의 단위 테스트가 검사한다.

## 실행

실행은 조회와 같은 권한을 요구한다. 그래서 public 에서 읽을 수 있는 사용자는 실행도 할 수 있고, 아무 권한도 없는 사용자만 거부된다. "아무 권한도 없는 사용자가 실행한다"에서 요청한 사용자는 그 권한을 받지 않은 사용자다.

`time_window` 값과 `time_range` 값은 다른 값이다. `time_window` 값은 템플릿의 플레이스홀더에 들어가는 문자열이고, `time_range` 값은 instant query 인지 range query 인지를 결정한다. 둘을 함께 지정할 수 있고 어느 쪽도 다른 쪽을 우선 적용하지 않는다.

`time_window` 값을 요청, 프리셋, 서버 기본값 중 어디에서 가져오는지와 `options` column 의 레이블 허용 목록 검사는 시나리오로 두지 않는다. 어느 쪽도 adapter 와 데이터베이스가 결과를 변경하지 않고 service 의 단위 테스트가 검사한다. 생성 절의 템플릿 검사와 같은 이유다.

Prometheus 가 거부하는 시나리오는 빈 질의로 구성한다. 레이블 플레이스홀더만 있는 템플릿은 렌더러를 통과하지만 레이블 없이 렌더링하면 빈 질의가 되고, Prometheus 는 빈 질의를 문법 에러로 거부한다.

존재하지 않는 id 는 superadmin 과 그 밖의 사용자에게 서로 다른 이유로 거부된다. 권한 검사가 먼저 실행되는데 없는 row 에는 부여된 권한도 없으므로, 그 검사를 통과하는 superadmin 만 "대상 없음"을 본다. 실행의 "대상 없음"은 service 가 프리셋을 직접 읽어서 반환하는 것이라 수정과 삭제의 "대상 없음"과 같은 종류가 아니다.

Prometheus 의 에러를 실행은 그대로 전파하고, 미리 보기는 평가 실패로 변환해 전파한다. 실행과 미리 보기 절의 "Prometheus 가 질의를 거부한다"가 서로 다른 에러로 거부되는 이유다.

## 미리 보기

미리 보기는 요청에서 템플릿만 읽는다. 레이블도 `time_window` 값도 받지 않으므로 mock 서버가 받는 질의는 항상 빈 레이블과 서버 기본 `time_window` 값이다. row 가 생기지 않는다는 것은 시나리오가 확인하지 않는다. 미리 보기는 저장소의 쓰기 경로를 거치지 않는다.

미리 보기는 이 adapter 에서 유일하게 superadmin 인지 검사하는 읽기라, monitor 역할이 성공하는 시나리오가 여기에만 있다.

## 삭제

이 adapter 에는 row 를 남기는 삭제가 없다. 삭제하면 row 가 사라지고 되살리는 호출도 없다. 삭제는 영구 삭제다. 옛 GraphQL mutation 과 REST 경로는 deprecated 이고 같은 호출로 이어진다.

deployment 의 자동 확장 규칙이 프리셋을 참조할 수 있다. 프리셋을 삭제하면 그 규칙은 남고 `prometheus_query_preset_id` 가 NULL 이 된다. 규칙을 미리 저장해 두려면 deployment 까지 생성해야 하므로, 그 시나리오는 `../deployment/KNOWLEDGE.md` 에 자동 확장 규칙 절이 생길 때 그쪽에 둔다.

## 여럿 수정

템플릿 검사는 항목마다 한다. 검사에 걸린 항목만 실패 목록에 오고 나머지는 수정된다.

## 여럿 삭제

여럿 연산은 호출 전체를 거부하지 않는다. 처리한 프리셋은 처리된 목록에, 처리하지 못한 항목은 id 와 이유를 실패 목록에 담는다.
