# session_group adapter: 배경

규칙은 상위 디렉터리의 `AGENTS.md` 에 있다. 이 문서와 실행 결과가 어긋나면 문장을 먼저 의심한다.

세션 그룹은 프로젝트와 세션 그룹 소유자 아래에 생성된다. 그래서 세션 그룹 하나를 읽고 변경하는 호출과 프로젝트에 세션 그룹을 생성하는 호출은 권한 그래프가 검사하고, 전체 검색은 전역 superadmin 역할이 검사한다.

세션 그룹은 두 가지다. 사용자가 생성한 세션 그룹과, 배포가 레플리카 그룹을 생성할 때 함께 생성되어 그 레플리카 그룹이 참조하는 세션 그룹이다. 뒤의 것은 배포와 함께 관리된다. 사용자에게 노출하는 읽기(하나 읽기, 여럿 읽기, 스코프 검색)는 배포의 레플리카 그룹이 참조하는 세션 그룹을 권한이 있어도 없는 것으로 응답하고, 배치 정책 변경과 영구 삭제는 사용 중이라는 것으로 거부한다. 전체 검색만 두 가지를 함께 보여준다.

공통 계약(대상 존재, 일괄 구성, 페이지)은 프레임워크 계약 테스트가 확인한다. 이 문서에는 연산마다 대표 성공과 대표 실패, 그리고 세션 그룹 규칙이 만드는 차이만 적는다.

## 하나 읽기

마지막 row 에서 사용자는 그 세션 그룹에 대한 읽기 권한도 갖는다. 따라서 거부 이유가 권한이 아니라 대상 없음이어야 한다.

## 여럿 읽기

여럿 읽기는 호출 전체를 거부하지 않고 항목마다 응답한다. 배포의 레플리카 그룹이 참조하는 세션 그룹은 없는 세션 그룹과 같은 빈 값으로 응답한다.

없는 id 의 row 에서는 superadmin 이 호출한다. 권한 검사는 id 마다 권한 그래프를 검사하는데, 그래프에 없는 id 는 권한을 확인할 수 없어 일반 사용자에게는 권한 부족으로 응답한다. 검사를 통과하는 사용자여야 읽기의 응답(빈 값)을 볼 수 있다.

## 전체 검색

전체 검색의 호출은 권한 그래프가 아니라 역할이 검사한다. 그래서 superadmin row 를 요청한 사용자는 superadmin 이다. 다른 시나리오가 미리 저장한 세션 그룹과 섞이지 않게 프로젝트 기준으로 필터링해 조회한다.

## 스코프 검색

스코프 하나라도 권한이 없으면 나머지를 보여주지 않고 검색 전체를 거부한다.

스코프 여럿은 OR 로 합친다. 마지막 row 에서 자기가 생성한 첫 프로젝트의 세션 그룹은 사용자 스코프로만, 다른 사용자가 생성한 세션 그룹은 프로젝트 스코프로만 접근할 수 있다. 그래서 둘 다 나와야 OR(논리합) 로 합친 결과가 맞다.

## 생성

세션 그룹이 프로젝트와 생성한 사용자 아래에 들어간 것은 응답에 나오지 않는다. 테스트가 실행 뒤 데이터베이스에서 세션 그룹 수, 세션 그룹 노드 수, 그 노드를 가진 프로젝트와 사용자의 수를 센다. 프로젝트 아래에 들어가야 그 프로젝트의 스코프 검색에 나온다.

읽기 권한 row 는 생성이 읽기 권한으로 통과하지 않는다는 것을 보인다. 다른 프로젝트 row 는 생성 권한이 세션 그룹을 생성할 프로젝트에 있어야 한다는 것을 보인다.

## 영구 삭제

세션 그룹과 그래프 노드가 사라진 것, 멤버 세션이 남은 것은 응답에 나오지 않는다. 테스트가 실행 뒤 데이터베이스에서 세션 그룹 수, 세션 그룹 노드 수, 세션 그룹이 있는 세션과 없는 세션의 수를 센다.

배포의 레플리카 그룹이 참조하는 세션 그룹 row 에서 사용자는 그 세션 그룹에 대한 영구 삭제 권한도 갖는다. 따라서 거부 이유가 권한이 아니라 사용 중이어야 한다.

읽기 권한 row 는 영구 삭제가 읽기 권한으로 통과하지 않는다는 것을 보인다. 아무 권한도 없는 row 와 짝을 이룬다.

## 배치 정책 변경

- 권한 row 의 짝은 같은 사용자가 같은 스코프에서 받은 권한만 다르다. 읽기 권한으로는 변경할 수 없다.
- 배포의 레플리카 그룹이 가진 세션 그룹은 생성한 사용자의 스코프에도 생성된다. 변경 권한을 가진 사용자만 이 거부에 도달하므로, 거부 이유는 권한이 아니라 배포가 그 세션 그룹을 사용 중이어야 한다.
- 변경할 수 있는 항목은 배치 방향과 강제 수준 둘뿐이다. 둘 다 생략하고 호출하면 요청 형식에서 거부된다.
- 변경된 정책은 이후 배치되는 멤버부터 따른다. 스케줄러가 배치할 때마다 세션 그룹 정책을 읽기 때문이고, 이미 배치된 멤버는 옮기지 않는다.
