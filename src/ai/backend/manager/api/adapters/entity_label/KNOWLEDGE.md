# entity_label 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 어긋나면 문장 쪽을 먼저
의심한다.

라벨은 어느 엔티티에나 붙는 `key=value` 한 쌍이다. 라벨 자체는 권한을 갖지 않고, 모든 호출은
라벨이 붙는 엔티티의 권한으로 답한다. 쓰기는 그 엔티티의 수정 권한, 읽기는 조회 권한이다.
슈퍼관리자는 모든 검사를 통과한다.

호출은 여섯이다. 하나를 설정, 여럿을 설정, 하나를 삭제, 여럿을 삭제, 이름 지은 엔티티들의
라벨 검색, 이미 손에 든 엔티티 하나의 라벨 검색. 단건 쓰기는 통째로 답하거나 통째로 거부되고,
일괄 쓰기는 엔티티마다 또는 라벨마다 따로 답한다.

여럿을 설정, 여럿을 삭제는 이름이 복수인 GQL mutation 과 `partial-bulk-` 로 시작하는 REST 경로로
부른다. 단수 이름의 mutation 과 `bulk-` 경로는 deprecated 이고 같은 호출로 잇는다.

엔티티 타입은 배선된 것만 이름 지을 수 있다. 배선되지 않은 타입을 든 요청은 어느 호출이든
잘못된 요청으로 통째로 거부된다. 일괄 쓰기도 예외가 아니다. 그것은 엔티티 하나의 결과가 아니라
요청 자체의 잘못이기 때문이다.

## 하나를 설정

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 엔티티 수정 권한을 받은 사용자가 라벨을 붙인다 | 엔티티 하나, 그 엔티티에 수정 권한을 받은 사용자 | 키와 값으로 설정 | 그 엔티티에 붙은 라벨 노드 |
| 같은 키를 다시 설정하면 값이 바뀐다 | 그 키의 라벨이 이미 붙은 엔티티, 수정 권한을 받은 사용자 | 같은 키에 다른 값으로 설정 | 같은 라벨의 값만 바뀐 노드. 라벨 id는 그대로다 |
| 아무 권한도 없는 사용자가 라벨을 붙인다 | 엔티티 하나, 아무 권한도 없는 사용자 | 키와 값으로 설정 | 권한 부족으로 거부 |
| 조회 권한만 받은 사용자가 라벨을 붙인다 | 엔티티 하나, 그 엔티티에 조회 권한만 받은 사용자 | 키와 값으로 설정 | 권한 부족으로 거부 |
| 배선되지 않은 타입에 붙인다 | 사용자 한 명 | 없는 타입 이름으로 설정 | 잘못된 요청으로 거부 |
| 권한 검사를 끄면 누구나 붙일 수 있다 | 권한 검사 비활성화, 아무 권한도 없는 사용자 | 키와 값으로 설정 | 그 엔티티에 붙은 라벨 노드 |

엔티티가 실제로 있는지는 보지 않는다. 라벨 행은 엔티티 행을 외래 키로 가리키지 않으므로, 권한
검사를 통과한 호출은 없는 id에도 라벨을 쓴다. 슈퍼관리자가 없는 id에 라벨을 붙이는 호출은 그래서
성공한다. 슈퍼관리자가 아닌 사용자는 없는 엔티티에 권한을 받을 수 없으므로 권한 부족으로
거부된다.

키나 값이 비어 있거나 길이 제한을 넘는 요청은 시나리오로 두지 않는다. 요청 타입이 이미
거부하므로 어댑터가 보장하는 것이 아니다.

## 여럿을 설정

한 요청에 엔티티 여럿과 키 여럿을 담는다. 답은 엔티티마다 하나다. 한 엔티티에 붙일 키들은 함께
쓰이거나 함께 거부된다. 실패 목록은 요청 항목 단위다. 거부된 엔티티에 붙이려던 키마다 엔티티,
키, 이유를 든 항목 하나가 온다.
호출 자체는 거부되지 않는다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 엔티티 둘에 키 둘을 붙인다 | 엔티티 둘, 둘 다에 수정 권한을 받은 사용자 | 엔티티 둘 × 키 둘 | 라벨 노드 넷이 반환되고 실패 목록은 비어 있다 |
| 한 엔티티에만 권한이 있다 | 엔티티 둘, 한쪽에만 수정 권한을 받은 사용자 | 엔티티 둘 × 키 둘 | 권한 있는 엔티티의 라벨 노드 둘이 반환되고, 다른 엔티티는 키마다 하나씩 실패 항목 둘로 온다 |
| 아무 권한도 없는 사용자가 붙인다 | 엔티티 둘, 아무 권한도 없는 사용자 | 엔티티 둘 × 키 하나 | 반환된 노드는 없고, 엔티티 둘 다 실패 목록에 온다. 아무것도 쓰이지 않는다 |
| 같은 엔티티가 여러 항목에 나온다 | 엔티티 하나, 수정 권한을 받은 사용자 | 같은 엔티티에 키 둘 | 라벨 노드 둘이 반환되고 실패 목록은 비어 있다 |
| 이미 붙은 키를 다시 붙인다 | 그 키의 라벨이 붙은 엔티티, 수정 권한을 받은 사용자 | 같은 키에 다른 값 | 값만 바뀐 같은 라벨의 노드 |
| 배선되지 않은 타입이 하나라도 섞여 있다 | 엔티티 하나, 수정 권한을 받은 사용자 | 있는 타입 하나와 없는 타입 하나 | 잘못된 요청으로 통째로 거부. 아무것도 쓰이지 않는다 |
| 권한 검사를 끄면 누구나 붙일 수 있다 | 권한 검사 비활성화, 아무 권한도 없는 사용자 | 엔티티 둘 × 키 하나 | 라벨 노드 둘이 반환되고 실패 목록은 비어 있다 |

실패 목록의 이유는 문자열이고, 문자열은 바뀌어도 되는 값이다. 시나리오는 이유가 있다는 것만
본다.

## 하나를 삭제

라벨은 자기 id로 이름 짓는다. 어느 엔티티가 답하는지는 행을 먼저 읽어 알아내고, 그 읽기는
엔티티의 조회 권한을 묻는다. 없는 id와 조회 권한이 없는 엔티티의 라벨은 같은 이유로 거부된다.
id가 있는지를 응답으로 알 수 없게 하기 위해서다. 슈퍼관리자는 이 병합을 거치지 않으므로 없는
id는 대상 없음으로 거부된다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 라벨을 뗀다 | 라벨이 붙은 엔티티, 그 엔티티에 수정 권한을 받은 사용자 | 라벨 id로 삭제 | 떼어 낸 라벨 노드 |
| 조회 권한만 받은 사용자가 뗀다 | 라벨이 붙은 엔티티, 조회 권한만 받은 사용자 | 라벨 id로 삭제 | 권한 부족으로 거부 |
| 아무 권한도 없는 사용자가 뗀다 | 라벨이 붙은 엔티티, 아무 권한도 없는 사용자 | 라벨 id로 삭제 | 잘못된 요청으로 거부 |
| 없는 id를 뗀다 | 다른 라벨만 있음, 수정 권한을 받은 사용자 | 없는 id로 삭제 | 잘못된 요청으로 거부 |
| 슈퍼관리자가 없는 id를 뗀다 | 다른 라벨만 있음, 슈퍼관리자 | 없는 id로 삭제 | 대상을 찾을 수 없다는 이유로 거부 |
| 권한 검사를 끄면 누구나 뗄 수 있다 | 권한 검사 비활성화, 아무 권한도 없는 사용자 | 라벨 id로 삭제 | 떼어 낸 라벨 노드 |

## 여럿을 삭제

라벨 id 여럿을 한 번에 이름 짓는다. 답은 라벨마다 하나다. 엔티티들을 한 번에 읽고 엔티티마다
수정 권한을 묻는다. 거부된 엔티티의 라벨과 없는 id는 이유를 들고 실패 목록에 오고, 나머지는
떼어진 채 성공 목록에 온다. 호출 자체는 거부되지 않는다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 라벨 둘을 뗀다 | 라벨 둘이 붙은 엔티티, 수정 권한을 받은 사용자 | id 둘로 삭제 | 둘 다 성공 목록에, 실패 목록은 비어 있다 |
| 엔티티가 다른 라벨 둘을 뗀다 | 엔티티 둘에 라벨 하나씩, 둘 다에 수정 권한을 받은 사용자 | id 둘로 삭제 | 둘 다 성공 목록에 |
| 한 엔티티에만 권한이 있다 | 엔티티 둘에 라벨 하나씩, 한쪽에만 수정 권한을 받은 사용자 | id 둘로 삭제 | 권한 있는 쪽은 성공 목록에, 다른 쪽은 실패 목록에 |
| 있는 id 뒤에 없는 id를 붙인다 | 라벨 하나, 수정 권한을 받은 사용자 | 있는 id와 없는 id | 있는 것은 성공 목록에, 없는 id는 실패 목록에 |
| 전부 없는 id다 | 다른 라벨만 있음, 수정 권한을 받은 사용자 | 없는 id 둘 | 성공 목록은 비고, 둘 다 실패 목록에 |
| 아무 권한도 없는 사용자가 뗀다 | 라벨 둘이 붙은 엔티티, 아무 권한도 없는 사용자 | id 둘로 삭제 | 성공 목록은 비고, 둘 다 실패 목록에. 아무것도 떼어지지 않는다 |
| 권한 검사를 끄면 누구나 뗄 수 있다 | 권한 검사 비활성화, 아무 권한도 없는 사용자 | id 둘로 삭제 | 둘 다 성공 목록에 |

이름 지은 id가 모두 없을 때 하위 계층은 답할 엔티티가 없어 통째로 거부한다. 어댑터가 그것을 id마다
하나씩 실패 항목으로 되돌려 놓으므로, 호출자는 무엇을 이름 지었든 한 모양으로 읽는다. "전부 없는
id다" 시나리오가 그것을 증명한다.

## 검색

이름 지은 엔티티들의 라벨을 한 페이지로 읽는다. 엔티티마다 조회 권한을 묻고, 하나라도 거부되면
읽기 전체가 거부된다. 읽기는 통째로 서거나 통째로 넘어진다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 조회 권한을 받은 사용자가 엔티티 하나의 라벨을 읽는다 | 라벨 둘이 붙은 엔티티, 조회 권한을 받은 사용자 | 그 엔티티로 검색 | 라벨 둘 |
| 엔티티 둘의 라벨을 함께 읽는다 | 엔티티 둘에 라벨 하나씩, 둘 다에 조회 권한을 받은 사용자 | 엔티티 둘로 검색 | 라벨 둘 |
| 한 엔티티에만 권한이 있다 | 엔티티 둘에 라벨 하나씩, 한쪽에만 조회 권한을 받은 사용자 | 엔티티 둘로 검색 | 권한 부족으로 거부 |
| 키로 거른다 | 키가 다른 라벨 둘이 붙은 엔티티, 조회 권한을 받은 사용자 | 키 하나로 검색 | 그 키의 라벨 하나 |
| 라벨이 없는 엔티티를 읽는다 | 라벨 없는 엔티티, 조회 권한을 받은 사용자 | 그 엔티티로 검색 | 빈 페이지 |
| 아무 권한도 없는 사용자가 읽는다 | 라벨이 붙은 엔티티, 아무 권한도 없는 사용자 | 그 엔티티로 검색 | 권한 부족으로 거부 |
| 배선되지 않은 타입으로 읽는다 | 사용자 한 명 | 없는 타입 이름으로 검색 | 잘못된 요청으로 거부 |

이미 손에 든 엔티티 하나의 라벨을 읽는 호출은 같은 읽기를 엔티티 하나로 부른 것이다. 엔티티를
다시 이름 짓지 않고 노드가 스스로를 댄다는 점만 다르다. 시나리오는 검색 절의 엔티티 하나짜리
행과 같으므로 따로 두지 않는다.

## 아직 적지 않은 것

- 검색의 정렬과 커서 페이지. 페이지 크기 기본값과 다음 페이지 유무는 다른 엔티티의 검색과 같은
  장치를 쓰므로, 라벨에서 따로 증명할 것이 없다.
- 여럿을 설정할 때 한 요청 안에서 같은 엔티티에 같은 키를 두 번 적는 경우. 나중 것이 이기지만,
  요청이 잘못된 것이라 보장으로 적지 않는다.
