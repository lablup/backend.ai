# notification adapter: 배경

규칙은 상위 디렉터리의 `AGENTS.md` 에 있다. 이 문서와 실행 결과가 어긋나면 문장을 먼저 의심한다.

이 adapter 는 `notification_channel` 과 `notification_rule` 두 엔티티를 다룬다. 둘 다 어느 스코프에도 속하지 않게 생성된다. 생성과 검색은 호출한 사용자가 superadmin 인지 검사하고(검색은 monitor 도 통과한다), id 를 지정하는 조회, 수정, 삭제, 검증은 그 row 에 부여된 권한을 검사하지만 그 권한을 받을 방법이 없다. 따라서 어느 호출이든 superadmin 만 통과하지만 거부 이유가 서로 다르다.

규칙은 채널을 `channel_id` 값으로만 참조한다. 두 테이블을 잇는 외래 키가 없으므로 없는 채널 id 로 규칙을 생성할 수 있고, 규칙이 참조하는 채널을 삭제해도 규칙은 남는다.

호출자는 요청과 별도로 `created_by` 값을 준다. 생성된 row 의 `created_by` 값은 그 값이다.

## 채널 생성

`spec` 에 `webhook` 과 `email` 을 모두 주면 `webhook` 쪽을 사용한다. adapter 가 `spec` 을 먼저 읽고 `channel_type` 값은 따로 저장하므로, 둘이 어긋난 요청은 row 를 작성한 뒤 그 row 를 다시 읽어 응답을 만드는 자리에서 명세 형식 검사에 걸려 거부된다. 같은 트랜잭션 안이라 작성한 row 는 되돌려진다.

이름이 비어 있거나 길이 제한을 넘는 요청은 시나리오로 두지 않는다. 요청 타입이 이미 거부한다.

"monitor 가 생성한다"는 검색 절의 "monitor 가 검색한다"와 짝이다. 같은 사용자가 검색은 할 수 있고 생성은 할 수 없다.

## 채널 조회

monitor 는 검색은 통과하지만 id 로 하나를 조회하지는 못한다. 검색은 superadmin 검사가 읽기에 한해 monitor 를 통과시키는 반면, id 조회는 권한 검사이고 monitor 에게도 부여된 권한이 없기 때문이다.

존재하지 않는 id 는 superadmin 과 그 밖의 사용자에게 서로 다른 이유로 거부된다. 권한 검사가 먼저 실행되는데 없는 row 에는 부여된 권한도 없으므로, 그 검사를 통과하는 superadmin 만 대상을 찾을 수 없어 거부된다. 아래 절의 없는 id 시나리오도 모두 같다.

한 번에 여럿을 조회할 때 없는 id 는 빈 항목으로, 권한이 없는 id 는 거부가 담긴 항목으로 온다. 둘을 구분해 담으므로 권한이 없는 사용자에게 row 가 없다고 응답하지 않는다.

## 채널 수정

`channel_type` 값은 변경할 수 없다. `spec` 만 변경할 수 있으므로 `webhook` 채널에 `email` `spec` 을 주면 생성 절의 어긋난 요청과 같은 경로로 거부된다.

## 채널 삭제

삭제는 row 를 영구 삭제하는 연산이다. row 를 남기는 삭제는 없다. 규칙이 참조하는 채널을 삭제해도 차단되지 않는 것은 두 테이블 사이에 외래 키가 없기 때문이다.

수정과 영구 삭제는 접두어 없는 이름(`updateNotificationChannel`, `purgeNotificationChannel`)이 기본이고 권한 검사만 거친다. 옛 이름(`adminUpdateNotificationChannel`, `adminDeleteNotificationChannel`, `deleteNotificationChannel`)과 본문에 id 를 받는 옛 REST 삭제 경로는 같은 호출로 이어지는 deprecated 별칭이고 superadmin 검사를 그대로 거친다. 규칙도 같다.

## 여럿 채널 영구 삭제

여럿 연산은 호출 전체를 거부하지 않는다. 처리한 채널은 처리된 목록에, 처리하지 못한 항목은 id 와 이유를 실패 목록에 담는다. 규칙의 여럿 연산도 같다.

## 채널 검증

검증은 시험 메시지를 그 채널로 실제로 보낸다. 시나리오는 보내는 쪽을 받아 적기만 하는 mock 으로 교체하여 실행한다. 보내기가 실패했을 때의 거부는 mock 이 만들 수 없으므로 시나리오로 두지 않는다.

## 규칙 생성

`message_template` 값은 생성할 때 검사하지 않는다. 깨진 템플릿도 저장되고 검증에서야 거부된다.

## 규칙 검증

검증은 규칙과 그 채널을 읽고, 시험 데이터를 `rule_type` 의 형식으로 검사한 뒤, 템플릿을 렌더링해 채널로 보낸다. 시나리오는 보내는 쪽만 mock 으로 교체한다. 형식에 맞지 않는 시험 데이터와 렌더링할 수 없는 템플릿의 거부는 시나리오로 두지 않는다. adapter 와 데이터베이스가 결과를 변경하지 않고 service 의 단위 테스트가 검사한다.
