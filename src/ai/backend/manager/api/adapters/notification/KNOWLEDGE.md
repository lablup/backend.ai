# notification 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 어긋나면 문장 쪽을 먼저
의심한다.

이 어댑터는 `notification_channel`과 `notification_rule` 두 엔티티를 다룬다. 둘 다 어느 스코프에도
속하지 않게 만들어진다. 생성과 검색은 호출한 사용자가 슈퍼관리자인지 검사하고(검색은 모니터도
통과한다), id를 지정하는 조회·수정·삭제·검증은 그 행에 부여된 권한을 검사하지만 그 권한을 받을
방법이 없다. 그래서 어느 호출이든 슈퍼관리자만 통과하지만 거부 이유가 서로 다르다.

규칙은 채널을 `channel_id` 값으로만 가리킨다. 두 테이블을 잇는 외래 키가 없으므로, 없는 채널
id로 규칙을 만들 수 있고 규칙이 가리키는 채널을 지워도 규칙은 남는다.

호출자는 요청과 별도로 `created_by` 값을 준다. 생성된 행의 `created_by` 값은 그 값이다.

## 채널 생성

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 `webhook` 채널을 만든다 | 슈퍼관리자 | 이름과 `url` 값만 지정해 생성 | `enabled` 값은 true이고 `description` 값은 비어 있는 노드 전체 |
| `email` 채널을 만든다 | 슈퍼관리자 | SMTP 접속·보내는 사람·받는 사람·인증 계정을 지정해 생성 | `spec`에 인증 `username` 값은 있고 `password` 값은 없는 노드 전체 |
| `enabled` 값을 false로 지정해 만든다 | 슈퍼관리자 | `enabled` 값을 false로 지정해 생성 | `enabled` 값이 false인 노드 |
| `spec`에 `webhook`도 `email`도 주지 않는다 | 슈퍼관리자 | 빈 `spec`으로 생성 | 잘못된 입력으로 거부 |
| `channel_type` 값과 `spec` 종류가 어긋난다 | 슈퍼관리자 | `channel_type` 값은 `email`인데 `webhook` `spec`을 주고 생성 | 잘못된 입력으로 거부 |
| 슈퍼관리자가 아닌 사용자가 만든다 | 슈퍼관리자 아님 | 생성 | 역할 부족으로 거부 |
| 모니터가 만든다 | 모니터 | 생성 | 역할 부족으로 거부 |

`spec`에 `webhook`과 `email`을 둘 다 주면 `webhook` 쪽을 쓴다. 어댑터가 `spec`을 먼저 읽고
`channel_type` 값은 따로 저장하므로, 둘이 어긋난 요청은 행을 쓴 뒤 그 행을 다시 읽어 답을
만드는 자리에서 명세 형식 검사에 걸려 거부된다. 같은 트랜잭션 안이라 쓴 행은 되돌려진다.

이름이 비어 있거나 길이 제한을 넘는 요청은 시나리오로 두지 않는다. 요청 타입이 이미 거부한다.

"모니터가 만든다"는 검색 절의 "모니터가 검색한다"와 짝이다. 같은 사용자가 검색은 할 수 있고
생성은 할 수 없다.

모니터는 검색은 통과하지만 id로 하나를 조회하지는 못한다. 검색은 슈퍼관리자 검사가 읽기에 한해
모니터를 통과시키는 반면, id 조회는 권한 검사이고 모니터에게도 부여된 권한이 없기 때문이다.

존재하지 않는 id는 슈퍼관리자와 그 밖의 사용자에게 서로 다른 이유로 거부된다. 권한 검사가 먼저
실행되는데 없는 행에는 부여된 권한도 없으므로, 그 검사를 통과하는 슈퍼관리자만 대상을 찾을 수
없어 거부된다. 아래 절들의 없는 id 시나리오도 모두 같다.

한 번에 여럿을 조회할 때 없는 id는 빈 항목으로, 권한이 없는 id는 거부가 담긴 항목으로 온다.
둘을 구분해 담으므로, 권한이 없는 사용자에게 행이 없다고 답하지 않는다.

| 슈퍼관리자가 삭제한다 | 규칙 하나, 슈퍼관리자 | 삭제 | 삭제한 id를 담은 응답 |
| 존재하지 않는 id를 삭제한다 | 다른 규칙만 있음, 슈퍼관리자 | 삭제 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 삭제한다 | 같은 규칙, 아무 권한도 없음 | 삭제 | 권한 부족으로 거부 |

## 규칙 검증

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 시험 데이터로 검증한다 | `session.started` 규칙 하나, 슈퍼관리자 | `rule_type`에 맞는 시험 데이터를 주고 검증 | 템플릿에 데이터를 넣어 만든 문자열 |
| 가리키는 채널이 없는 규칙을 검증한다 | 없는 채널 id를 가리키는 규칙 하나, 슈퍼관리자 | 검증 | 대상을 찾을 수 없어 거부 |
| 존재하지 않는 id를 검증한다 | 다른 규칙만 있음, 슈퍼관리자 | 검증 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 검증한다 | 같은 규칙, 아무 권한도 없음 | 검증 | 권한 부족으로 거부 |

검증은 규칙과 그 채널을 읽고, 시험 데이터를 `rule_type`의 형식으로 검사한 뒤, 템플릿을 그려
채널로 보낸다. 시나리오는 보내는 쪽만 대역으로 바꾼다. 형식에 맞지 않는 시험 데이터와 그릴 수
없는 템플릿의 거부는 시나리오로 두지 않는다. 어댑터와 데이터베이스가 결과를 바꾸지 않고, 서비스의
단위 테스트가 검사한다.

## 아직 적지 않은 것

없다. 어댑터가 제공하는 `create_channel`, `get_channel`, `update_channel`, `delete_channel`,
`search_channels`, `validate_channel`, `batch_load_channels_by_ids`, `create_rule`, `get_rule`,
`update_rule`, `delete_rule`, `search_rules`, `validate_rule`, `batch_load_rules_by_ids`가 모두
위에 있다.

`batch_load_fields`는 모든 어댑터가 물려받는 공용 도우미이지 이 엔티티의 호출이 아니다. 레포트가
이 호출도 함께 세지만 적을 시나리오는 없다.
