# 폴더 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 어긋나면 문장 쪽을
먼저 의심한다.

폴더는 언제나 어떤 스코프 안에 만들어진다. 개인 폴더는 만든 사람 본인의 스코프에, 프로젝트
폴더는 그 프로젝트의 스코프에 생긴다. 그래서 도메인과 달리 권한을 받은 일반 사용자로 세우는
시나리오가 성립하고, 권한을 확인하는 시나리오의 호출자는 superadmin이 아니다.

요청을 막을 수 있는 것은 네 가지다.

| 요청 | 무엇이 막는가 |
|---|---|
| 만들기, 내 폴더 검색, 프로젝트 폴더 검색 | 요청이 지정한 스코프의 권한 — 개인 폴더는 호출자 본인, 프로젝트 폴더는 그 프로젝트 |
| id로 하나 읽기·지우기·되살리기 | 그 폴더 하나에 걸린 권한 |
| 전체 검색, id 여러 개 읽기 | 권한이 아니라 superadmin 역할 |
| 지우기 | 위의 권한에 더해, 키페어 정책이 그 스토리지 호스트에서 지우기를 허용해야 한다 |

RBAC enforcement를 끄면 표의 첫째·둘째는 검사 없이 통과하지만, superadmin 역할을 확인하는
셋째와 키페어 정책을 확인하는 넷째는 그대로 막는다. 어떤 요청이 어떤 권한을 요구하는지는
액션 레이어의 `KNOWLEDGE.md`에 있다.

**첫째 줄과 둘째 줄의 범위는 서로 다르다.** 개인 폴더는 그 사람의 개인 프로젝트 안에
만들어지고, 만들어진 뒤에는 그 프로젝트를 기준으로 권한을 판정한다. 호출자 본인 스코프에
받은 권한으로는 폴더를 만들 수는 있지만 이미 만들어진 폴더에는 미치지 않는다. 그래서 이미
존재하는 폴더를 읽고 지우고 되살리는 시나리오는 도메인 스코프의 역할로 권한을 준다.

지우기는 폴더를 휴지통으로 옮길 뿐이라 되살리면 그대로 돌아온다. 그래서 지우기와 되살리기가
같은 권한을 쓴다. 다만 되살리기는 RBAC과 별개로 누가 지웠는지를 한 번 더 확인하므로, 폴더
전체에 권한을 받은 사람이라도 남이 지운 폴더는 되살릴 수 없다. 폴더를 완전히 삭제하는 요청은
따로 있으며 여기서 다루지 않는다.

## 만들기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 내 폴더로 만든다 | 호출자 본인 스코프에 생성 권한 | 호스트를 지정해 만들기 | 그 사용자가 소유자인 폴더 전체 |
| 프로젝트를 지정해 프로젝트 폴더로 만든다 | 그 프로젝트에 생성 권한 | 프로젝트를 지정해 만들기 | 소유자가 그 프로젝트인 폴더, 개인 소유자는 없음 |
| 이름만 주고 만든다 | 호출자 본인 스코프에 생성 권한 | 이름만 주고 만들기 | 지정하지 않은 값은 기본값이 되고, 폴더는 기본 호스트에 놓인다 |
| 아무 권한도 받지 않은 사용자가 만든다 | 호출자 본인 스코프에 아무 권한도 없음 | 만들기 | 권한 부족으로 거부 |
| RBAC enforcement를 끄면 권한 없이도 만들어진다 | RBAC enforcement 꺼짐, 호출자 본인 스코프에 아무 권한도 없음 | 만들기 | 만들어진다 |
| 자원 정책의 허용 개수를 다 쓴 사용자가 만든다 | 호출자 본인 스코프에 생성 권한, 폴더를 하나만 허용하는 사용자 자원 정책, 이미 하나 보유 | 만들기 | 허용 개수를 넘어 거부 |
| 살아 있는 폴더의 이름으로 만든다 | 같은 이름의 자기 폴더가 하나 있음 | 그 이름으로 만들기 | 이름이 중복되어 거부 |
| 휴지통에 있는 폴더의 이름으로 만든다 | 같은 이름의 자기 폴더를 휴지통에 보내 둠 | 그 이름으로 만들기 | 이름이 중복되어 거부 |
| 완전히 사라진 폴더의 이름으로 만든다 | 같은 이름의 자기 폴더가 저장소에서 완전히 사라짐 | 그 이름으로 만들기 | 그 이름을 쓴 새 폴더가 만들어진다 |

이름은 한 프로젝트 안에서 한 번만 설 수 있는데, 그 판정에서 빠지는 상태는 저장소에서 완전히
사라진 것뿐이다. 휴지통에 있는 동안에는 이름이 아직 잡혀 있다. 되살리면 그 이름으로 돌아와야
하기 때문이다.

## 프로젝트에 만들기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 프로젝트 권한을 받은 사용자가 만든다 | 그 프로젝트에 생성 권한 | 프로젝트 아래 만들기 | 소유자가 그 프로젝트인 폴더 전체 |
| 아무 권한도 받지 않은 사용자가 만든다 | 그 프로젝트에 아무 권한도 없음 | 프로젝트 아래 만들기 | 권한 부족으로 거부 |
| 자기 개인 프로젝트를 대상으로 만든다 | 사용자를 만들 때 딸려 만들어진 개인 프로젝트, 거기에 생성 권한 | 그 프로젝트 아래 만들기 | 스토리지 호스트 권한 부족으로 거부 |

개인 프로젝트는 어떤 스토리지 호스트도 허용하지 않은 채 만들어진다. 생성 spec에 개인
프로젝트를 대상으로 삼지 말라는 검사가 따로 있지만, 호스트 검사가 행을 쓰기 전에 먼저 돌아
거기까지 닿지 않는다.

## 읽기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 읽기 권한을 받은 사용자가 자기 폴더를 읽는다 | 도메인 스코프에 폴더 읽기 권한 | id로 조회 | 만들어 둔 그대로의 폴더 전체 |
| superadmin이 남의 폴더를 읽는다 | 다른 사람이 만든 폴더, 그 폴더에 읽기 권한 없음 | id로 조회 | 그 폴더 전체 |
| 아무 권한도 받지 않은 사용자가 남의 폴더를 읽는다 | 그 폴더에 아무 권한도 없음 | id로 조회 | 권한 부족으로 거부 |
| 어떤 폴더도 가리키지 않는 id로 읽는다 | 호출자 본인 스코프에 읽기 권한 | 없는 id로 조회 | 권한 부족으로 거부 |
| superadmin이 어떤 폴더도 가리키지 않는 id로 읽는다 | superadmin 역할 | 없는 id로 조회 | 대상이 없어 거부 |

같은 요청이라도 superadmin인지 아닌지에 따라 거부 사유가 달라진다. 권한 검사가 먼저
실행되는데 존재하지 않는 행에는 걸린 권한도 없으므로, 그 검사를 건너뛰는 superadmin만 대상이
없다는 답을 보게 된다. 아래 절에 나오는 없는 id 시나리오도 모두 마찬가지다.

monitor 역할이 통과하는 것은 읽기 요청뿐이다. 역할을 확인하는 쪽에서 읽기 요청만 monitor에게
열어두기 때문이다.

전체 검색은 REST 라우트와 GraphQL 리졸버가 각각 어댑터 앞에서 한 번 더 막으므로, 일반
사용자의 요청이 실제로 여기까지 오지는 않는다. 위의 거부 두 줄은 그 앞단을 지나 어댑터에
닿았을 때도 안쪽이 여전히 막는가를 본다.

## id 여러 개 한 번에 읽기

답은 요청한 id와 같은 길이의 목록이라, 찾은 것과 찾지 못한 것이 한 답에 섞여 온다. 그래서
항목마다 따로 확인한다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 있는 것과 없는 것을 섞어 읽는다 | superadmin 역할, 폴더 둘과 어떤 폴더도 가리키지 않는 id 하나 | 셋을 함께 조회 | 요청한 순서 그대로, 없는 id 자리는 비어서 온다 |
| superadmin이 아닌 사용자가 읽는다 | superadmin 아님, 도메인 스코프에 폴더 읽기 권한 | 자기 폴더 id로 조회 | 필요한 역할이 없어 거부 |
| 빈 목록을 준다 | 아무 권한도 없음 | 빈 목록으로 조회 | 비어 있음 |

빈 목록을 주면 권한이 없어도 거부되지 않는다. 어댑터가 권한 검사에 이르기 전에 빈 답을
돌려주기 때문이다.

이 호출은 GraphQL이 다른 엔티티에서 폴더를 딸려 읽을 때 쓰는 자리라, 사용자가 직접 부르는
API가 아니다. 위의 거부 줄은 그 호출자가 역할을 확인하지 않고 불렀을 때 안쪽이 막는가를
본다.

| 시나리오 | 상황 | 요청 | 결과 |

| 지운 사람이 되살린다 | 도메인 스코프에 폴더 지우기 권한, 자기가 지운 폴더 | 되살리기 | 되살린 폴더를 가리키는 답 |
| 아무 권한도 받지 않은 사용자가 되살린다 | 그 폴더에 아무 권한도 없음 | 남이 지운 폴더 되살리기 | 권한 부족으로 거부 |
| 권한이 있어도 남의 폴더는 되살릴 수 없다 | 도메인 스코프에 폴더 지우기 권한, 그러나 남이 지운 폴더 | 되살리기 | 대상이 없어 거부 |

권한이 없는 것과 키페어 정책이 그 호스트를 허용하지 않는 것은 서로 다른 사유로 거부된다.
그래야 호출자가 무엇 때문에 막혔는지 알 수 있다.

## 여러 개 지우기

요청에 담긴 id를 하나씩 순서대로 지운다. 중간에 하나가 막혀도 앞서 지운 것을 되돌리지 않고,
실패한 것만 따로 모아 함께 돌려준다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 자기 폴더 둘을 한 번에 지운다 | 도메인 스코프에 폴더 지우기 권한, 키페어 정책도 허용, 자기 폴더 둘 | 둘을 함께 지우기 | 둘 다 지워지고 실패한 것은 없음 |
| 권한이 미치는 것과 미치지 않는 것을 함께 지운다 | 자기 도메인에 폴더 지우기 권한, 다른 도메인에 있는 남의 폴더 하나 | 둘을 함께 지우기 | 권한이 미치는 것만 지워지고, 나머지는 실패 목록에 담겨 온다 |

## 아직 적지 않은 것

아래 열한 개는 폴더 안의 파일을 다루거나 스토리지 프록시를 거치는 호출이다. 따로 조사한다.

`clone`, `create_download_session`, `create_upload_session`, `delete_files`, `deploy`,
`get_folder_usage`, `list_files`, `mkdir`, `move_file`, `purge`, `bulk_purge`.

`batch_load_fields`는 모든 어댑터가 물려받는 공용 도우미일 뿐 이 엔티티의 호출이 아니다.
실행 보고서에는 함께 집계되지만 여기에 적을 내용은 없다.
