# resource_group adapter: 배경

규칙은 상위 디렉터리의 `AGENTS.md` 에 있다. 이 문서와 실행 결과가 어긋나면 문장을 먼저 의심한다.

자원 그룹은 어느 스코프에도 속하지 않게 생성되고, 그 자신이 에이전트와 세션의 스코프다. 생성과 전체 검색은 호출한 사용자가 superadmin 인지 검사한다(검색은 monitor 도 통과한다). 그룹 하나를 대상으로 하는 조회, 수정, 영구 삭제는 그 그룹에 부여된 권한을 검사하는데, 그룹이 자기 스코프이므로 그룹에 부여한 역할이 그 권한을 준다. 그래서 이 문서의 권한 짝은 superadmin 과 그 밖의 사용자가 아니라, 그룹에 부여한 역할을 받은 사용자와 받지 않은 사용자다.

이름으로 id 를 찾는 호출은 인증만 확인한다. 따라서 존재하지 않는 이름은 누구에게나 대상을 찾을 수 없어 거부되고, 권한 검사는 찾은 뒤에야 온다.

세션이 자원 그룹에 접근하는 길은 셋이다. 도메인에 추가한 것, 프로젝트에 추가한 것, 사용자의 키페어에 추가한 것. 허용 목록 호출들은 그중 도메인과 프로젝트에 추가하는 relation 을 작성하고 읽는다.

## 생성

요청의 `domain_name` 값은 읽지 않는다. 그룹은 어느 도메인에도 추가되지 않은 채 생성되고, 도메인에 추가하는 것은 허용 목록 절의 호출이다.

기본 그룹은 하나뿐이다. 둘째 기본 그룹을 생성하는 시나리오는 현재 코드에서 실패하므로 실행에서 제외했다(BA-7946, 기본 그룹 중복 제약 위반). 생성 경로는 그것을 강제하는 제약의 위반을 이름 중복과 구분하지 않아 둘째 기본 그룹을 이름 중복으로 거부한다. 수정 경로는 구분한다(수정 절). 시나리오에는 수정 경로와 같은 이유로 거부되는 결과를 기대값으로 적어 두었다. 수정되면 다시 실행에 포함한다.

## 조회

존재하지 않는 이름은 superadmin 에게도 그 밖의 사용자에게도 같은 이유로 거부된다. 이름으로 id 를 찾는 호출이 인증만 확인하고, 권한 검사는 찾은 id 에 대해서만 실행되기 때문이다. 아래 절의 존재하지 않는 이름 시나리오도 모두 같다.

자원 현황은 `ALIVE` 상태이고 스케줄 가능한 에이전트의 `agent_resource` row 를 합한 것이다. 에이전트가 없는 그룹은 세 값 모두 항목이 없다.

## 이름으로 id 찾기

다른 엔티티의 REST handler 와 GQL resolver 는 자원 그룹 이름을 id 로 변환할 때 이를 먼저 호출한다.

지금은 권한이 없는 사용자에게도 id 를 반환한다. 권한 없는 사용자가 이름으로도 접근하지 못하게 권한을 검사하는 조회로 변경할 예정이며, 뒤따르는 호출의 영향과 함께 자원 그룹 작업에서 정한다.

## 검색

스코프 검색은 지정한 스코프마다 그 스코프 안에서 자원 그룹을 읽을 권한이 있어야 한다. 도메인 스코프의 응답은 그 도메인에 추가한 그룹뿐이다. superadmin 도 추가되지 않은 그룹은 보지 못한다.

## 수정

수정은 id 를 받는다. 설정 수정은 이름으로 id 찾기를 먼저 호출하고 같은 수정으로 잇는다. 이름을 받는 옛 REST 경로와 GQL mutation 도 같은 경로다. 그래서 둘은 같은 권한 검사를 거치고 같은 노드를 반환하며, 변경할 수 있는 필드도 같다. 수정 요청 타입의 `name`, `total_resource_slots`, `allowed_vfolder_hosts`, `integration_name`, `resource_policy` 값은 adapter 가 읽지 않는다.

## 여럿 수정

## 영구 삭제

영구 삭제만 있고 row 를 남기는 삭제는 없다. `is_active` 값을 false 로 변경하는 것이 그 역할을 대신한다. 영구 삭제는 id 를 받는다. 이름을 받는 옛 REST 경로와 GQL mutation 은 이름으로 id 찾기를 먼저 호출하고 같은 호출로 잇는다.

## 여럿 영구 삭제

여럿 연산은 호출 전체를 거부하지 않는다. 처리한 그룹은 처리된 목록에, 처리하지 못한 항목은 id 와 이유를 실패 목록에 담는다.

## 허용 목록

도메인 쪽과 프로젝트 쪽, 그리고 그룹 쪽에서 같은 relation 을 작성하고 읽는 호출 여덟이다.

도메인 쪽과 프로젝트 쪽에서 호출하는 것은 그룹 이름을 id 로 변환하는 단계가 superadmin 검사를 거치므로 superadmin 만 통과한다. 그룹 쪽에서 호출하는 것은 이름을 인증만으로 변환하고, relation 을 작성하는 단계가 양쪽 스코프의 권한을 검사한다. 어느 쪽이든 아무 권한도 없는 사용자는 거부되지만 이유가 다르다.

제거하는 쪽의 존재하지 않는 이름은 양쪽이 다르게 다룬다. 도메인 쪽에서 존재하지 않는 그룹 이름을 제거하면 건너뛰지만, 그룹 쪽에서 존재하지 않는 도메인 이름을 제거하면 거부된다. 도메인 이름을 id 로 변환하는 단계가 내는 에러를 그 호출이 잡지 않기 때문이다.

프로젝트의 허용 목록 조회는 세 스코프에서 읽는다: 호출한 사용자의 도메인, 지정한 프로젝트, 호출한 사용자 자신. 세 스코프 모두에서 자원 그룹을 읽을 권한이 있어야 통과하므로, 이 문서는 superadmin 이 통과하는 것과 아무 권한도 없는 사용자가 거부되는 것만 고정한다.

## fair share 설정

설정 조회는 그룹을 전체 검색으로 찾으므로 superadmin 검사를 먼저 거친다. 그룹에 부여한 읽기 역할로는 그룹 자체는 읽어도 이 설정은 읽지 못한다. 수정은 그룹을 대상으로 하는 권한 검사만 거치므로 수정 역할로 통과한다.

`resource_weights` 의 항목을 그 그룹 용량에 있는 자원으로 제한하는 검사는 시나리오로 두지 않는다. service 가 판단하고 service 의 단위 테스트가 검사한다. 수정이 반환하는 노드에는 이 설정이 담기지 않는다.

## 기본 옵션

processor 이름은 배포 코디네이터와 스케줄 코디네이터에 등록된 것에서 읽는다. 시나리오는 두 코디네이터를 등록된 processor 만 응답하는 mock 으로 교체하여 실행한다.
