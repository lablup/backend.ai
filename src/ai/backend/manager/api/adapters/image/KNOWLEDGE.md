# 이미지 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 다르면 문장을 먼저
의심한다.

호출을 막는 검사가 세 가지다.

| 검사 | 적용되는 호출 | 확인하는 것 |
|---|---|---|
| 전역 역할 | 검색, 별칭, 수정 | 슈퍼관리자인가 |
| 엔티티 권한 | 소프트 삭제, 복원, 완전 삭제 | 그 이미지에 권한을 받았는가 |
| 소유권 | 소프트 삭제, 복원, 완전 삭제 | 커스터마이즈된 이미지이고 호출자가 만들었는가 |

뒤의 두 검사는 차례로 실행된다. 엔티티 권한을 통과해도 소유권 검사가 남는다. 권한 검사
비활성화 설정은 엔티티 권한까지만 적용되고 소유권 검사에는 영향을 주지 않는다.

이미지는 컨테이너 레지스트리에 속한다. 레지스트리 자체의 호출은
`../container_registry/KNOWLEDGE.md`에 있다.

## 검색

|---|---|---|---|

| 페이지 크기를 생략한다 | 이미지 51개, 전역 역할 있음 | 크기 없이 조회 | 50개까지 반환되고 다음 페이지가 있다고 알린다 |
| 슈퍼관리자가 아닌 사용자가 검색한다 | 이미지 2개, 전역 역할 없음 | 전체 조회 | 역할 부족으로 거부 |

요청 타입은 커서 필드를 받지만 이 검색은 사용하지 않는다. 크기와 오프셋만 읽는다. 커서를 함께
지정하면 지금은 조용히 무시된다. 무시할지 사용할지 정하고 시나리오를 적는다.

커서를 사용하는 검색은 따로 있다. 이미지와 별칭에 하나씩이다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 커서로 앞에서부터 읽는다 | 이미지 3개, 전역 역할 있음 | 커서 조회 | 앞의 2개와 다음 페이지 표시 |
| 상위 계층이 지정한 조건이 먼저 적용된다 | 레지스트리가 서로 다른 이미지 2개씩, 전역 역할 있음 | 한 레지스트리로 좁힌 조회 | 그 레지스트리의 이미지만 남는다 |
| 페이지 방식을 두 가지 함께 지정한다 | 이미지 2개, 전역 역할 있음 | 크기와 커서를 함께 지정한 조회 | 입력이 잘못되어 거부 |
| 커서 값이 잘못되어 있다 | 이미지 2개, 전역 역할 있음 | 잘못된 커서로 조회 | 커서가 잘못되어 거부 |
| 별칭이 하나도 없다 | 별칭 없음, 전역 역할 있음 | 별칭 조회 | 빈 응답 |
| 등록된 별칭을 검색한다 | 별칭 1개, 전역 역할 있음 | 별칭 조회 | 그 별칭이 반환된다 |
| 슈퍼관리자가 아닌 사용자가 별칭을 검색한다 | 이미지 2개, 전역 역할 없음 | 별칭 조회 | 역할 부족으로 거부 |

3번과 4번은 요청 타입이 막는 것이 아니다. 어댑터가 페이지 방식을 고르는 과정에서 발생한다.
어댑터가 보장하는 동작이므로 시나리오로 남긴다.

상위 계층이 지정하는 조건은 커서를 사용하는 검색에만 있다. 호출자가 준 필터보다 먼저
적용되므로 2번이 그 순서를 확인한다.

## 소프트 삭제와 복원

소프트 삭제는 행을 지우지 않는다. 상태만 삭제됨으로 바꾸므로 복원할 수 있다. 행까지 없애는
것은 아래의 완전 삭제다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이미지를 소프트 삭제한다 | 살아 있는 이미지, 전역 역할 있음 | 소프트 삭제 | 삭제됨 상태가 담긴 노드. 행은 남는다 |
| 커스텀 이미지의 소유자가 자기 것을 소프트 삭제한다 | 자기가 만든 커스텀 이미지, 그 이미지에 삭제 권한 있음 | 소프트 삭제 | 삭제됨 상태가 담긴 노드 |
| 소프트 삭제한 것을 복원한다 | 삭제된 이미지, 전역 역할 있음 | 복원 | 대상을 찾을 수 없어 거부 |
| 삭제하지 않은 것을 복원한다 | 살아 있는 이미지, 전역 역할 있음 | 복원 | 살아 있는 상태 그대로 |
| 존재하지 않는 id를 소프트 삭제한다 | 다른 이미지만 있음, 전역 역할 있음 | 소프트 삭제 | 대상을 찾을 수 없어 거부 |
| 존재하지 않는 id를 복원한다 | 다른 이미지만 있음, 전역 역할 있음 | 복원 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 받지 않은 사용자가 소프트 삭제한다 | 커스터마이즈되지 않은 이미지, 아무 권한도 없음 | 소프트 삭제 | 권한 부족으로 거부 |
| 아무 권한도 받지 않은 사용자가 복원한다 | 커스터마이즈되지 않은 이미지, 아무 권한도 없음 | 복원 | 권한 부족으로 거부 |
| 권한을 받아도 소유자가 없는 이미지는 삭제하지 못한다 | 커스터마이즈되지 않은 이미지, 그 이미지에 삭제 권한 있음 | 소프트 삭제 | 접근 금지로 거부 |
| 권한 검사를 꺼도 소유자가 없는 이미지는 삭제하지 못한다 | 권한 검사 비활성화, 아무 권한도 없음, 커스터마이즈되지 않은 이미지 | 소프트 삭제 | 접근 금지로 거부 |
| 완전 삭제 중인 이미지를 소프트 삭제한다 | 완전 삭제 중인 이미지, 전역 역할 있음 | 소프트 삭제 | 대상을 찾을 수 없어 거부 |

9번과 10번이 이 어댑터의 핵심이다. 엔티티 권한을 통과한 사용자가 소유권 검사에서 거부된다.
권한 검사를 비활성화해도 소유권 검사는 그대로 동작한다.

그래서 권한 부족과 접근 금지를 하나로 합치면 안 된다. 합치면 권한을 더 받으면 되는 상황인지를
호출자가 구분할 수 없다.

커스터마이즈되지 않은 이미지에는 소유자가 없다. 슈퍼관리자 외에는 아무도 삭제할 수 없다.

복원은 삭제된 이미지에 접근하지 못한다. id로 이미지를 조회하는 지점이 살아 있는 것만 대상으로
삼기 때문에, 삭제된 것을 복원하려 하면 대상을 찾을 수 없다고 응답한다. 살아 있는 것을 복원하는
경우만 성공하는데 그것은 아무것도 바꾸지 않는다. 완전 삭제 중인 이미지도 같은 이유로 조회되지
않아서, 상태 변경을 막는 검사에는 이 어댑터를 통해 도달할 수 없다.

복원을 이대로 둘지 정해야 한다. 위 시나리오는 현재 동작을 적은 것이고, 구현을 고치면 두
시나리오가 함께 바뀐다.

## 별칭 등록과 해제

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 별칭을 등록한다 | 이미지 1개, 전역 역할 있음 | 별칭 등록 | 별칭 id와 이름, 그리고 그 이미지의 id |
| 등록한 별칭을 해제한다 | 별칭이 등록되어 있음, 전역 역할 있음 | 별칭 해제 | 해제된 별칭과 그 이미지의 id |
| 존재하지 않는 id에 별칭을 등록한다 | 다른 이미지만 있음, 전역 역할 있음 | 별칭 등록 | 대상을 찾을 수 없어 거부 |
| 이미 사용 중인 별칭을 등록한다 | 그 별칭이 다른 이미지에 등록되어 있음, 전역 역할 있음 | 별칭 등록 | 유니크 제약 위반으로 거부 |
| 존재하지 않는 별칭을 해제한다 | 다른 별칭만 있음, 전역 역할 있음 | 별칭 해제 | 대상을 찾을 수 없어 거부 |
| 커스텀 이미지의 소유자가 자기 것에 별칭을 등록한다 | 자기가 만든 커스텀 이미지, 그 이미지에 권한 있음 | 별칭 등록 | 역할 부족으로 거부 |
| 슈퍼관리자가 아닌 사용자가 별칭을 해제한다 | 별칭이 등록되어 있음, 전역 역할 없음 | 별칭 해제 | 역할 부족으로 거부 |

별칭은 이미지에 딸린 값이다. 그런데 등록과 해제를 막는 검사는 전역 역할이다. 소프트 삭제를
막는 검사와 달라서, 같은 이미지에 대해 두 검사가 서로 다르게 거부한다. 6번이 그 차이를
확인한다. 커스텀 이미지의 소유자라도 자기 이미지에 별칭을 등록할 수는 없다.

가속기 목록만 세 가지 요청을 구분한다. 생략, 비우기, 값 지정이다. 나머지 필드는 생략과 값
지정 두 가지뿐이라 세 번째 경우는 가속기에만 둔다.

## 응답이 호출자에 따라 달라진다

에이전트 설치 정보를 숨기는 설정이 있다. 켜져 있으면 슈퍼관리자가 아닌 호출자에게는 그 정보가
빈 값으로 반환된다.

같은 이미지를 같은 요청으로 조회해도 응답이 갈린다는 뜻이다. 그래서 검색의 성공 시나리오를
호출자별로 따로 둔다. 이 차이는 이 어댑터에만 있다.

## 저장한 값 그대로 반환되지 않는 필드

| 필드 | 반환되는 값 | 이유 |
|---|---|---|
| `config_digest`, `metadata.digest` | 저장한 값 뒤에 공백이 채워진 값 | 컬럼 폭이 72자로 고정이다. 실제 다이제스트는 71자라 항상 한 칸이 남는다 |
| `registry_id` | 컨테이너 레지스트리의 uuid를 `ArtifactRegistryID`로 감싼 값 | 이미지가 속한 곳은 컨테이너 레지스트리인데 어댑터가 다른 종류의 id로 감싼다. `EntityIdentifier`의 동등성은 종류까지 비교하므로 `ContainerRegistryID`와 같지 않다 |

둘 다 현재 동작을 적은 것이다. 구현을 고치면 시나리오의 해당 항목도 함께 바뀐다.

## 아직 적지 않은 것

이 어댑터가 자기 이름으로 제공하는 11개 호출은 모두 위에 있다.

응답에 담기지 않는 변화는 이 표로 확인할 수 없다. 완전 삭제가 별칭까지 함께 지우는 것이
그렇다. 응답은 삭제된 이미지뿐이고, 별칭이 남았는지 확인하려면 그다음 조회가 필요하다.
시나리오 하나가 호출 하나를 검증하는 단위이므로 그 조회는 여기 들어가지 않는다.

`batch_load_fields`는 아직 어느 시나리오도 호출하지 않는다. 어댑터 공통 기반이 제공하는
것이고, 필드 행을 DataLoader로 조회하는 지점이라 이미지의 어느 필드를 읽을지 정한 뒤에 적는다.
