# image 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 다르면 문장을 먼저
의심한다.

호출을 막는 검사는 슈퍼관리자 검사, 이미지 권한 검사, 커스텀 이미지 작성자 검사다.

| 검사 | 적용되는 호출 | 확인하는 것 |
|---|---|---|
| 슈퍼관리자 검사 | 검색, 별칭, 수정 | 호출자가 슈퍼관리자인가 |
| 이미지 권한 검사 | soft delete, 복원, 완전 삭제, 여러 ID 조회(ID마다) | 호출자가 해당 이미지의 권한을 받았는가 |
| 커스텀 이미지 작성자 검사 | soft delete, 복원, 완전 삭제 | 이미지가 커스텀 이미지이고 호출자가 만들었는가 |

이미지 권한 검사와 커스텀 이미지 작성자 검사는 차례로 실행된다. 이미지 권한 검사를 통과해도
커스텀 이미지 작성자 검사가 남는다.

`image` 엔티티는 컨테이너 레지스트리에 속한다. 레지스트리 자체의 시나리오는
`../container_registry/KNOWLEDGE.md`에 있다.

## 검색

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 필터 없이 검색한다 | 이미지 2개, 호출자는 슈퍼관리자 | 전체 조회 | 이미지 2개가 반환되고 전체 개수는 2 |
| 이름으로 필터링한다 | 이미지 3개, 호출자는 슈퍼관리자 | 한 이미지의 이름으로 조회 | 해당 이미지 1개만 반환 |
| 상태로 필터링한다 | `ALIVE` 상태인 이미지와 `DELETED` 상태인 이미지, 호출자는 슈퍼관리자 | `ALIVE` 상태인 이미지 조회 | `ALIVE` 상태인 이미지만 반환 |
| 정렬과 오프셋을 함께 지정한다 | 이미지 4개, 호출자는 슈퍼관리자 | 이름 내림차순, 첫 항목 제외, 2개 조회 | 정렬된 결과의 두 번째와 세 번째 항목, 이전 페이지와 다음 페이지가 모두 있음 |
| 페이지 크기를 생략한다 | 이미지 51개, 호출자는 슈퍼관리자 | 크기 없이 조회 | 50개가 반환되고 다음 페이지가 있음 |
| 커서만 지정한다 | 이미지 3개, 호출자는 슈퍼관리자 | 크기와 오프셋 없이 커서로 2개 조회 | 앞의 2개가 반환되고 다음 페이지가 있음 |
| 크기와 커서를 함께 지정한다 | 이미지 3개, 호출자는 슈퍼관리자 | 크기 1과 커서를 함께 지정한 조회 | 커서는 무시되고 크기대로 1개 |
| 슈퍼관리자가 아닌 사용자가 검색한다 | 이미지 2개, 호출자는 일반 사용자 | 전체 조회 | 역할 부족으로 거부 |

요청 타입은 크기·오프셋과 커서를 모두 받는다. 커서만 지정하면 커서로 읽고, 크기나 오프셋이
하나라도 있으면 오프셋으로 읽는다. 커서만 지정한 요청에 첫 페이지를 반환하면 결함이다.

커서를 사용하는 검색은 이미지 검색과 별칭 검색으로 따로 있다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 커서로 앞에서부터 읽는다 | 이미지 3개, 호출자는 슈퍼관리자 | 커서 조회 | 앞의 2개가 반환되고 다음 페이지가 있음 |
| 호출 측이 지정한 조건이 먼저 적용된다 | 레지스트리가 서로 다른 이미지 2개씩, 호출자는 슈퍼관리자 | 한 레지스트리로 좁힌 조회 | 해당 레지스트리의 이미지만 반환 |
| 크기와 커서를 함께 지정한다 | 이미지 2개, 호출자는 슈퍼관리자 | 크기와 커서를 함께 지정한 조회 | 잘못된 입력으로 거부 |
| 커서 값이 잘못되어 있다 | 이미지 2개, 호출자는 슈퍼관리자 | 잘못된 커서로 조회 | 잘못된 커서로 거부 |
| 별칭이 하나도 없다 | 별칭 없음, 호출자는 슈퍼관리자 | 별칭 조회 | 빈 목록 |
| 등록된 별칭을 검색한다 | 별칭 1개, 호출자는 슈퍼관리자 | 별칭 조회 | 해당 별칭이 반환 |
| 이미지별로 별칭을 필터링하고 정렬한다 | 이미지 2개에 별칭 3개, 호출자는 슈퍼관리자 | 한 이미지의 별칭을 이름 내림차순으로 조회 | 해당 이미지의 별칭만 내림차순으로 반환 |
| 슈퍼관리자가 아닌 사용자가 별칭을 검색한다 | 이미지 2개, 호출자는 일반 사용자 | 별칭 조회 | 역할 부족으로 거부 |

크기와 커서를 함께 지정하거나 커서 값이 잘못된 경우의 거부는 요청 타입이 막는 것이
아니다. 어댑터가 페이지 방식을 고르는 과정에서 발생한다. 어댑터가 보장하는 동작이므로
시나리오로 남긴다.

호출 측이 지정하는 기본 조건은 커서를 사용하는 검색에만 있다. 요청의 필터보다 먼저
적용되므로 "호출 측이 지정한 조건이 먼저 적용된다"가 그 순서를 확인한다.

## 여러 ID로 조회

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 존재하는 ID와 존재하지 않는 ID를 섞어 조회한다 | 이미지 2개, 호출자는 슈퍼관리자 | ID 3개를 한 번에 조회 | 요청 순서대로 반환되고 없는 ID 위치는 비어 있음 |
| 같은 ID를 두 번 조회한다 | 이미지 1개, 호출자는 슈퍼관리자 | 같은 ID 2개를 한 번에 조회 | 같은 이미지가 두 위치에 반환 |
| 빈 목록을 전달한다 | 호출자는 슈퍼관리자 | 빈 ID 목록 조회 | 빈 목록 |
| 아무 권한도 받지 않은 사용자가 조회한다 | 이미지 2개, 호출자는 아무 권한도 없는 사용자 | ID 3개를 한 번에 조회 | ID마다 권한 부족으로 거부 |
| 별칭 ID를 섞어 조회한다 | 별칭 1개, 호출자는 슈퍼관리자 | 별칭 ID 2개를 한 번에 조회 | 요청 순서대로 반환되고 없는 ID 위치는 비어 있음 |
| 빈 별칭 ID 목록을 전달한다 | 호출자는 슈퍼관리자 | 빈 별칭 ID 목록 조회 | 빈 목록 |
| 아무 권한도 받지 않은 사용자가 별칭 ID로 조회한다 | 별칭 1개, 호출자는 아무 권한도 없는 사용자 | 별칭 ID 2개를 한 번에 조회 | 있는 별칭 위치는 권한 부족으로 거부, 없는 ID 위치는 비어 있음 |

여러 ID 조회는 요청 전체가 아니라 ID마다 이미지 권한 검사를 거친다. 거부된 ID 위치에는 예외
객체가 반환되고, 나머지 ID 위치에는 조회 결과가 그대로 반환된다.

## soft delete와 복원

soft delete는 행을 지우지 않는다. 상태만 `DELETED` 값으로 바꾸므로 복원할 수 있다. 행까지 없애는
것은 아래의 완전 삭제다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 이미지를 soft delete한다 | `ALIVE` 상태인 이미지, 호출자는 슈퍼관리자 | soft delete | `DELETED` 상태인 노드, 행은 남음 |
| 커스텀 이미지 작성자가 자기 이미지를 soft delete한다 | 자기가 만든 커스텀 이미지, 해당 이미지의 삭제 권한 있음 | soft delete | `DELETED` 상태인 노드 |
| soft delete한 것을 복원한다 | `DELETED` 상태인 이미지, 호출자는 슈퍼관리자 | 복원 | `ALIVE` 상태인 노드 |
| 삭제하지 않은 것을 복원한다 | `ALIVE` 상태인 이미지, 호출자는 슈퍼관리자 | 복원 | `ALIVE` 상태 그대로 |
| 존재하지 않는 ID를 soft delete한다 | 다른 이미지만 있음, 호출자는 슈퍼관리자 | soft delete | 대상을 찾을 수 없어 거부 |
| 존재하지 않는 ID를 복원한다 | 다른 이미지만 있음, 호출자는 슈퍼관리자 | 복원 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 받지 않은 사용자가 soft delete한다 | 커스텀 이미지가 아닌 이미지, 호출자는 아무 권한도 없는 사용자 | soft delete | 권한 부족으로 거부 |
| 아무 권한도 받지 않은 사용자가 복원한다 | 커스텀 이미지가 아닌 이미지, 호출자는 아무 권한도 없는 사용자 | 복원 | 권한 부족으로 거부 |
| 일반 이미지는 권한을 받은 사용자도 삭제하지 못한다 | 커스텀 이미지가 아님, 호출자에게 이미지 삭제 권한 있음 | soft delete | 커스텀 이미지 작성자 검사에서 거부 |
| RBAC 권한 검사를 꺼도 작성자 검사는 남는다 | RBAC 권한 검사 비활성화, 커스텀 이미지가 아님 | soft delete | 커스텀 이미지 작성자 검사에서 거부 |
| `PURGING` 상태인 이미지를 soft delete한다 | `PURGING` 상태인 이미지, 호출자는 슈퍼관리자 | soft delete | 대상을 찾을 수 없어 거부 |

"일반 이미지는 권한을 받은 사용자도 삭제하지 못한다"는 이미지 권한 검사와 커스텀 이미지 작성자
검사가 별개임을 확인한다.

그래서 이미지 권한 검사의 거부(권한 부족)와 커스텀 이미지 작성자 검사의 거부(접근 금지)를 하나로
합치면 안 된다. 합치면 권한을 더 받으면 되는 상황인지를 호출자가 구분할 수 없다.

커스텀 이미지가 아니면 작성자 검사를 통과할 수 없다. 슈퍼관리자만 이 검사를 건너뛰고
삭제할 수 있다. 이는 이미지와 레지스트리의 RBAC 소유 관계를 의미하지 않는다.

복원은 `DELETED` 상태인 이미지와 `ALIVE` 상태인 이미지 모두에 적용된다. `ALIVE` 상태인
이미지를 복원하면 아무것도 바뀌지 않는다.

## 별칭 등록과 해제

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 별칭을 등록한다 | 이미지 1개, 호출자는 슈퍼관리자 | 별칭 등록 | 별칭 ID와 이름, 해당 이미지의 ID |
| 등록한 별칭을 해제한다 | 별칭이 등록되어 있음, 호출자는 슈퍼관리자 | 별칭 해제 | 해제된 별칭과 해당 이미지의 ID |
| 존재하지 않는 ID에 별칭을 등록한다 | 다른 이미지만 있음, 호출자는 슈퍼관리자 | 별칭 등록 | 대상을 찾을 수 없어 거부 |
| 이미 사용 중인 별칭을 등록한다 | 해당 별칭이 등록되어 있음, 호출자는 슈퍼관리자 | 별칭 등록 | 제약 위반으로 거부 |
| 존재하지 않는 별칭을 해제한다 | 다른 별칭만 있음, 호출자는 슈퍼관리자 | 별칭 해제 | 대상을 찾을 수 없어 거부 |
| 커스텀 이미지 작성자가 자기 이미지에 별칭을 등록한다 | 자기가 만든 커스텀 이미지, 해당 이미지의 권한 있음 | 별칭 등록 | 역할 부족으로 거부 |
| 슈퍼관리자가 아닌 사용자가 별칭을 해제한다 | 별칭이 등록되어 있음, 호출자는 일반 사용자 | 별칭 해제 | 역할 부족으로 거부 |

별칭은 이미지에 속한 값이다. 등록과 해제는 이미지 권한이 아니라 슈퍼관리자 검사로 보호된다.
soft delete는 이미지 권한 검사가, 별칭 등록은 슈퍼관리자 검사가 막으므로 같은 이미지라도 거부
이유가 다르다. "커스텀 이미지 작성자가 자기 이미지에 별칭을 등록한다"가 그 차이를 확인한다.
커스텀 이미지 작성자라도 자기 이미지에 별칭을 등록할 수는 없다.

| 값을 하나도 지정하지 않는다 | 이미지 1개, 호출자는 슈퍼관리자 | 빈 수정 | 아무것도 바뀌지 않은 노드 |
| `supported_accelerators` 필드를 비운다 | `accelerators` 값이 있는 이미지, 호출자는 슈퍼관리자 | `supported_accelerators` 필드를 비우는 수정 | `accelerators` 필드가 비어 있는 노드 |
| `supported_accelerators` 필드에 가속기 이름을 지정한다 | `accelerators` 값이 없는 이미지, 호출자는 슈퍼관리자 | `supported_accelerators` 필드에 가속기 이름을 지정하는 수정 | `accelerators` 필드에 해당 이름이 담긴 노드 |
| `name`·`registry`·`image`·`architecture`·`size_bytes`·`type`·`config_digest`·`is_local` 필드를 함께 수정한다 | 이미지 1개, 호출자는 슈퍼관리자 | `name`·`registry`·`image`·`architecture`·`size_bytes`·`type`·`config_digest`·`is_local` 수정 | 지정한 값이 담긴 노드 |
| 레이블과 리소스 제한을 함께 수정한다 | 이미지 1개, 호출자는 슈퍼관리자 | 레이블과 CPU 하한·상한 수정 | 지정한 레이블과 리소스 제한이 담긴 노드 |
| 존재하지 않는 ID를 수정한다 | 다른 이미지만 있음, 호출자는 슈퍼관리자 | 태그 수정 | 대상을 찾을 수 없어 거부 |
| 슈퍼관리자가 아닌 사용자가 수정한다 | 이미지 1개, 호출자는 일반 사용자 | 태그 수정 | 역할 부족으로 거부 |

생략, 비우기, 값 지정을 구분하는 것은 `supported_accelerators` 필드뿐이다. 나머지 필드는 생략과
값 지정만 받으므로 비우는 시나리오는 `supported_accelerators` 필드에만 둔다.
