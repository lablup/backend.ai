# 보존 정책 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 내용과 실행 결과가 어긋나면 문장 쪽을 먼저
의심한다.

보존 정책은 카테고리마다 하나이고 어느 스코프에도 속하지 않게 만들어진다. 생성과 검색은 전역
역할이 있어야 하고, 하나를 지정하는 조회·수정·삭제는 그 정책에 부여된 권한을 검사하는데 그
권한을 받을 방법이 없다. 두 경로 모두 슈퍼관리자만 통과하지만 거부 이유가 서로 다르고, 권한
검사 스위치에는 뒤의 경로만 반응한다.

다른 전역 카탈로그와 달리 하나를 조회하는 것도 권한 검사를 거친다. 인증만으로 조회되는
카탈로그와 같은 시나리오를 만들면 결과가 반대다.

## 생성

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 카테고리와 보존 일수만 지정해 생성한다 | 정책 없음, 전역 역할 있음 | 생성 | 활성 여부는 참이고 마지막 정리 시각은 비어 있는 노드 |
| 활성 여부를 꺼서 생성한다 | 정책 없음, 전역 역할 있음 | 활성 여부를 거짓으로 지정해 생성 | 비활성 상태가 담긴 노드 |
| 여덟 카테고리 각각으로 생성한다 | 정책 없음, 전역 역할 있음 | 카테고리마다 하나씩 생성 | 여덟이 모두 생성된다 |
| 같은 카테고리에 두 번 생성한다 | 그 카테고리의 정책이 있음, 전역 역할 있음 | 생성 | 카테고리 중복으로 거부 |
| 슈퍼관리자가 아닌 사용자가 생성한다 | 전역 역할 없음 | 생성 | 역할 부족으로 거부 |
| 모니터 역할이 생성한다 | 모니터 역할 | 생성 | 역할 부족으로 거부 |
| 권한 검사를 꺼도 슈퍼관리자가 아니면 생성할 수 없다 | 권한 검사 비활성화, 전역 역할 없음 | 생성 | 역할 부족으로 거부 |

마지막 정리 시각은 요청으로 정할 수 없다. 생성할 때 비어 있고 정리 루프가 나중에 채우며, 이
어댑터의 어느 호출도 그 값을 쓰지 않는다.

보존 일수가 하루보다 짧은 요청은 시나리오로 두지 않는다. 요청 타입이 이미 막기 때문이다.

모니터 역할 시나리오는 검색 절의 같은 시나리오와 짝이다. 같은 사용자가 검색은 할 수 있고
생성은 할 수 없다.

## 조회

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 id로 조회한다 | 정책 하나, 전역 역할 있음 | id로 조회 | 그 정책 전체 |
| 아무 권한도 없는 사용자가 조회한다 | 같은 정책, 아무 권한도 없음 | id로 조회 | 권한 부족으로 거부 |
| 존재하지 않는 id로 조회한다 | 다른 정책만 있음, 전역 역할 있음 | id로 조회 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 없는 id로 조회한다 | 다른 정책만 있음, 아무 권한도 없음 | id로 조회 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 조회된다 | 권한 검사 비활성화, 아무 권한도 없음 | id로 조회 | 그 정책 전체 |

존재하지 않는 id는 슈퍼관리자와 그 밖의 사용자에게 서로 다른 이유로 거부된다. 권한 검사가 먼저
실행되는데 없는 행에는 부여된 권한도 없으므로, 그 검사를 통과하는 슈퍼관리자만 "대상 없음"을
본다. 아래 절들의 없는 id 시나리오도 모두 같다.

## 검색

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 검색한다 | 카테고리가 다른 정책 둘, 전역 역할 있음 | 전체 조회 | 둘 다 집계된다 |
| 카테고리 필터로 검색한다 | 카테고리가 다른 정책 여럿, 전역 역할 있음 | 카테고리 필터 조회 | 그 카테고리의 정책 하나 |
| 활성 여부 필터로 검색한다 | 활성과 비활성이 섞여 있음, 전역 역할 있음 | 활성 필터 조회 | 활성인 정책만 남는다 |
| 모니터 역할이 검색한다 | 정책 둘, 모니터 역할 | 전체 조회 | 슈퍼관리자와 같은 응답 |
| 슈퍼관리자가 아닌 사용자가 검색한다 | 전역 역할 없음 | 전체 조회 | 역할 부족으로 거부 |

카테고리가 여덟뿐이라 정책도 여덟을 넘지 못한다. 열 건을 넘겨 다음 페이지를 확인하는 시나리오는
만들 수 없으므로 두지 않는다.

모니터 역할은 전역 역할 검사에서 읽기만 통과한다. 이 엔티티에서 그 차이를 보여 주는 짝은 검색의
모니터 시나리오와 생성의 모니터 시나리오다.

## 수정

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 보존 일수만 바꾼다 | 정책 하나, 전역 역할 있음 | 보존 일수 수정 | 일수는 새 값, 카테고리와 활성 여부는 그대로 |
| 활성 여부를 끈다 | 활성 정책, 전역 역할 있음 | 활성 여부 수정 | 비활성 상태가 담긴 노드 |
| 값을 하나도 지정하지 않는다 | 정책 하나, 전역 역할 있음 | 빈 수정 | 아무것도 바뀌지 않은 노드 |
| 이미 정책이 있는 카테고리로 바꾼다 | 카테고리가 다른 정책 둘, 전역 역할 있음 | 한쪽 카테고리를 다른 쪽 카테고리로 수정 | 카테고리 중복으로 거부 |
| 존재하지 않는 id를 수정한다 | 다른 정책만 있음, 전역 역할 있음 | 보존 일수 수정 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 수정한다 | 같은 정책, 아무 권한도 없음 | 보존 일수 수정 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 수정된다 | 권한 검사 비활성화, 아무 권한도 없음 | 보존 일수 수정 | 일수가 새 값인 노드 |

카테고리 중복 거부는 생성할 때와 수정할 때 서로 다른 오류로 온다. 생성은 이 엔티티의 오류로
거부하고, 수정은 저장소의 제약 위반을 그대로 전파한다. 시나리오를 적기 전에 하나로 맞출 것인지
정한다.

## 삭제

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 삭제한다 | 정책 하나, 전역 역할 있음 | 삭제 | 삭제한 id를 담은 응답 |
| 완전 삭제한다 | 정책 하나, 전역 역할 있음 | 완전 삭제 | 삭제와 같은 응답. 남는 행이 없다 |
| 존재하지 않는 id를 삭제한다 | 다른 정책만 있음, 전역 역할 있음 | 삭제 | 대상을 찾을 수 없어 거부 |
| 아무 권한도 없는 사용자가 삭제한다 | 같은 정책, 아무 권한도 없음 | 삭제 | 권한 부족으로 거부 |
| 아무 권한도 없는 사용자가 완전 삭제한다 | 같은 정책, 아무 권한도 없음 | 완전 삭제 | 권한 부족으로 거부 |
| 권한 검사를 끄면 권한 없이도 삭제된다 | 권한 검사 비활성화, 아무 권한도 없음 | 삭제 | 삭제한 id를 담은 응답 |

삭제와 완전 삭제는 같은 일을 한다. 둘 다 행을 지우고 soft delete는 없다. 이름이 둘인 것은 둘 다
이미 노출돼 있어 합치면 API 변경이 되기 때문이고, 그래서 둘을 각각 시나리오로 두어 같다는 것을
고정한다.

권한 검사를 끄는 시나리오들이 생성 절과 반대 결과를 갖는다. 조회·수정·삭제는 역할이 아니라 권한
그래프로 보호되므로 스위치가 영향을 준다. 같은 스위치로 아무 권한 없는 사용자가 정책을 조회하고
수정하고 삭제할 수 있게 되지만 생성할 수는 없다. 그것이 의도인지는 이 시나리오들을 실행해 본 뒤
정한다.

## 아직 적지 않은 것

없다. 어댑터가 제공하는 여섯 호출이 모두 위에 있다.

`batch_load_fields`는 모든 어댑터가 물려받는 공용 도우미이지 이 엔티티의 호출이 아니다. 레포트가
함께 세지만 적을 것이 없다.
