# deployment 어댑터 — 시나리오

규칙은 상위 디렉터리의 `AGENTS.md`에 있다. 여기 적힌 것과 실행 결과가 어긋나면 문장을 먼저
의심한다.

deployment는 프로젝트 스코프에 생긴다. 만드는 권한은 프로젝트에 걸리고, 만들어진 뒤에는
그 deployment 자체에 걸린다. 전역 훑기와 전체 리비전 새로 고침만 전역 역할이 지킨다.

deployment가 소유하는 행 — 리비전, 복제본과 경로, 접근 토큰, 배포 정책, 자동 확장 규칙 —
은 이 절에 적지 않는다. 그것들은 자기 스코프를 갖지 않고 소유 deployment로 인가되므로,
필드마다 절을 따로 둔다.

## 만들기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 생성 권한을 받은 사용자가 만든다 | 프로젝트 하나, 그 프로젝트에 생성 권한 있음 | 리비전 없이 만들기 | 그 프로젝트에 속한 deployment, 만든 사람이 소유와 세션 주인을 함께 갖는다 |
| 이름을 대지 않고 만든다 | 같은 프로젝트, 생성 권한 있음 | 이름 없이 만들기 | 만든 사람으로 지어진 이름이 붙는다 |
| 초기 리비전과 함께 만든다 | 생성 권한 있음, 모델 폴더와 이미지가 있음 | 초기 리비전을 함께 주고 만들기 | 리비전 하나가 딸린 deployment, 아직 현재 리비전은 없다 |
| 초기 리비전을 자동 활성으로 만든다 | 생성 권한 있음, 모델 폴더와 이미지가 있음 | 자동 활성으로 만들기 | 그 리비전이 현재 리비전이 된다 |
| 생성 권한이 없는 사용자가 만든다 | 같은 프로젝트, 생성 권한 없음 | 만들기 | 권한 부족으로 거부 |
| 다른 프로젝트의 생성 권한으로 만든다 | 생성 권한을 받은 프로젝트와 만들려는 프로젝트가 다름 | 만들기 | 권한 부족으로 거부 |
| 집행을 끄면 생성 권한 없이도 만들어진다 | 엔티티 권한 집행 꺼짐, 생성 권한 없음 | 만들기 | 만들어진다 |

집행을 끄는 줄이 도메인과 반대 결과를 갖는다. 이 문은 역할이 아니라 권한 그래프가 지키므로
스위치가 통한다. 도메인 쪽 같은 줄과 짝을 이루는 자리다.

만들기는 배포 정책 행을 함께 쓴다. 전략을 고르는 갈래가 셋이라 각각을 줄로 둔다 — 순차
설정을 준 경우, 청록 설정을 준 경우, 어느 설정도 주지 않고 전략 이름만 준 경우.

리비전 보관 개수는 요청이 정하지 못한다. 만들기가 값을 못박는다.

이름이 공백뿐인 요청과 복제 수가 음수인 요청은 줄로 두지 않는다. 요청 타입이 이미 막으므로
어댑터가 보장하는 것이 아니다.

답의 기본 배포 전략은 요청이 무엇을 골랐든 순차로 온다. 고른 전략은 배포 정책 쪽에 실린다.

## 읽기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 읽기 권한을 받은 사용자가 읽는다 | deployment 하나, 읽기 권한 있음 | id로 조회 | 그 deployment 전체 |
| 읽기 권한이 없는 사용자가 읽는다 | 같은 deployment, 읽기 권한 없음 | id로 조회 | 권한 부족으로 거부 |
| 아무것도 갖지 않은 id로 읽는다 | 읽기 권한 있음 | 없는 id로 조회 | 권한 부족으로 거부 |
| 슈퍼관리자가 아무것도 갖지 않은 id로 읽는다 | 슈퍼관리자 | 없는 id로 조회 | 대상 없음으로 거부 |
| 현재 리비전이 없는 것의 현재 리비전을 읽는다 | 리비전이 딸리지 않은 deployment, 읽기 권한 있음 | 현재 리비전 조회 | 현재 리비전이 없다는 이유로 거부 |
| 현재 리비전을 읽는다 | 현재 리비전이 있는 deployment, 읽기 권한 있음 | 현재 리비전 조회 | 그 리비전 |

없는 id가 슈퍼관리자와 그렇지 않은 사람에게 다른 것으로 거부된다. 권한 검사가 먼저 도는데
없는 행에는 걸린 권한도 없으므로, 그 검사를 지나가는 슈퍼관리자만 대상 없음을 본다. 아래
절의 없는 id 줄도 모두 같다.

현재 리비전 조회는 읽기 두 번을 이어 붙인 것이다. deployment를 읽을 권한만 있고 리비전을
읽을 수 없는 사람은 없으므로, 두 번째 문이 따로 무엇을 막지 않는다는 것을 줄로 둔다.

## 훑기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 슈퍼관리자가 전체를 훑는다 | 프로젝트 둘에 deployment 넷, 전역 역할 있음 | 전체 조회 | 넷을 모두 센다 |
| 슈퍼관리자가 아닌 사용자가 전체를 훑는다 | 전역 역할 없음, 훑기 권한만 있음 | 전체 조회 | 역할로 거부 |
| 만든 사람이 자기 것을 훑는다 | 두 사람이 각각 만든 deployment, 부르는 사람 자신의 스코프에 훑기 권한 있음 | 내 것 조회 | 자기가 만든 것만 나온다 |
| 권한 없이 자기 것을 훑는다 | 두 사람이 각각 만든 deployment, 부르는 사람 자신의 스코프에 훑기 권한 없음 | 내 것 조회 | 권한 부족으로 거부 |
| 프로젝트로 훑는다 | 프로젝트 둘에 deployment가 나뉘어 있고 한쪽에만 훑기 권한 있음 | 프로젝트 조회 | 그 프로젝트의 것만 나온다 |
| 훑기 권한이 없는 프로젝트로 훑는다 | 그 프로젝트에 훑기 권한 없음 | 프로젝트 조회 | 권한 부족으로 거부 |
| 상태로 걸러 훑는다 | 살아 있는 것과 지워지는 중인 것이 섞여 있음, 전역 역할 있음 | 상태 필터 조회 | 고른 상태의 것만 남는다 |
| id 여럿을 한 번에 집는다 | deployment 여럿이 있음, 전역 역할 있음 | id 목록으로 조회 | 목록 순서대로, 없는 id 자리는 비어서 온다 |

훑는 문이 셋이다. 전역 훑기는 역할이 지킨다. 프로젝트 훑기는 그 프로젝트에, 내 것 훑기는
부르는 사람 자신의 스코프에 걸린 훑기 권한이 지킨다. 내 것 훑기도 범위만 좁히지 않는다.

## 수정하기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 이름을 바꾼다 | deployment 하나, 수정 권한 있음 | 이름 수정 | 이름은 새 값, 나머지는 그대로 |
| 태그를 지운다 | 태그가 붙은 deployment, 수정 권한 있음 | 태그를 비우는 수정 | 태그가 없어진다 |
| 복제 수를 올린다 | 복제 수가 하나인 deployment, 수정 권한 있음 | 복제 수 수정 | 원하는 복제 수가 새 값이 된다 |
| 공개 여부를 바꾼다 | 공개가 아닌 deployment, 수정 권한 있음 | 공개 여부 수정 | 공개로 바뀐 상태를 실은 답 |
| 수정 권한이 없는 사용자가 수정한다 | 같은 deployment, 읽기 권한만 있음 | 이름 수정 | 권한 부족으로 거부 |
| 슈퍼관리자가 아무것도 갖지 않은 id를 수정한다 | 슈퍼관리자 | 없는 id의 이름 수정 | 대상 없음으로 거부 |

이름이 공백뿐인 요청은 줄로 두지 않는다. 만들기와 같이 요청 타입이 막는다.

요청 타입이 선호 도메인 이름과 배포 전략을 받지만 수정 경로가 그 둘을 쓰지 않는다. 지금은
조용히 버려진다. 줄을 적기 전에 버릴 것인지 쓸 것인지 정한다.

## 옵션 갈아끼우기

옵션은 배포 단계를 도는 처리기가 얼마나 기다리고 몇 번까지 다시 하는지다. 만들 때 리소스
그룹의 기본값을 베껴 두므로 비어 있는 적이 없고, 리소스 그룹 쪽이 나중에 바뀌어도 따라
움직이지 않는다. 이미 있는 deployment의 값을 바꾸는 문이 이것뿐인 이유다.

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 옵션을 갈아끼운다 | 리소스 그룹의 기본값을 그대로 물려받은 deployment, 수정 권한 있음 | 기본값과 처리기별 설정을 담아 갈아끼우기 | 준 것이 통째로 새 옵션이 되고, 답은 그 옵션만 싣는다 |
| 처리기별 설정을 하나도 주지 않는다 | 물려받은 처리기별 설정이 있는 deployment, 수정 권한 있음 | 기본값만 담아 갈아끼우기 | 물려받은 설정이 남지 않는다 |
| 등록되지 않은 처리기 이름을 준다 | 수정 권한 있음 | 그 이름을 담아 갈아끼우기 | 입력이 틀렸다는 이유로 거부 |
| 같은 처리기 이름을 두 번 준다 | 수정 권한 있음 | 갈아끼우기 | 입력이 틀렸다는 이유로 거부 |
| 수정 권한이 없는 사용자가 갈아끼운다 | 같은 deployment, 읽기 권한만 있음 | 갈아끼우기 | 권한 부족으로 거부 |

갈아끼우기는 합치지 않는다. 부분 수정으로 읽히기 쉬운 자리라 주지 않은 것이 사라진다는 줄을
따로 둔다.

처리기 이름은 살아 있는 등록 목록에 대고 본다. 시나리오가 이름을 리터럴로 적지 않고 등록된
것에서 읽는다.

답이 deployment 전체가 아니라 갈아끼운 옵션만이다. 다른 호출과 검사 범위가 다르다.

## 리비전 활성화

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 리비전을 활성화한다 | 리비전 둘이 있고 하나가 현재인 deployment, 수정 권한 있음 | 다른 하나를 활성화 | 그것이 배포 중 리비전이 되고, 직전 현재 리비전을 함께 답한다 |
| 이미 현재인 리비전을 다시 활성화한다 | 현재 리비전이 있는 deployment, 수정 권한 있음 | 그것을 활성화 | 이미 현재라는 이유로 거부 |
| 배포가 도는 중에 다시 활성화한다 | 배포 중 리비전이 있는 deployment, 수정 권한 있음 | 또 다른 리비전을 활성화 | 새 것이 배포 중 리비전을 덮어쓴다 |
| 아무것도 갖지 않은 리비전 id로 활성화한다 | 그 deployment에 수정 권한 있음 | 활성화 | 대상 없음으로 거부 |
| 수정 권한이 없는 사용자가 활성화한다 | 같은 deployment, 읽기 권한만 있음 | 활성화 | 권한 부족으로 거부 |
| 슈퍼관리자가 전체를 새로 고친다 | 살아 있는 deployment 둘, 전역 역할 있음 | 전체 새로 고침 | 둘 다 새 리비전을 얻고 그것이 현재가 된다 |
| 하나가 실패해도 나머지가 돈다 | 현재 리비전이 없는 것이 섞여 있음, 전역 역할 있음 | 전체 새로 고침 | 실패한 것과 성공한 것을 함께 답한다 |
| 슈퍼관리자가 아닌 사용자가 전체를 새로 고친다 | 전역 역할 없음, 모든 deployment에 수정 권한 있음 | 전체 새로 고침 | 역할로 거부 |

활성화는 리비전이 그 deployment의 것인지 보지 않는다. 다른 deployment의 리비전 id를 주면
어떻게 되어야 하는지 정하고 줄을 적는다.

전체 새로 고침은 일부만 성공하는 것이 설계다. 하나가 실패해도 나머지가 돈다는 것을 줄로 둔다.

## 복제 맞추기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| 수정 권한을 받은 사용자가 복제를 맞춘다 | 원하는 복제 수와 실제가 어긋난 deployment, 수정 권한 있음 | 복제 맞추기 | 맞추기 시작했다는 답 |
| 수정 권한이 없는 사용자가 맞춘다 | 같은 deployment, 읽기 권한만 있음 | 복제 맞추기 | 권한 부족으로 거부 |

맞추기는 요청 안에서 끝나지 않는다. 답은 시작했다는 것뿐이고, 복제본이 실제로 뜨는 것은
다른 자리에서 본다.

## 지우기

| 시나리오 | 상황 | 요청 | 결과 |
|---|---|---|---|
| soft-delete 권한을 받은 사용자가 지운다 | deployment 하나, soft-delete 권한 있음 | 지우기 | 지우기 시작했다는 답 |
| 수정 권한만 받은 사용자가 지운다 | 수정 권한 있음, soft-delete 권한 없음 | 지우기 | 권한 부족으로 거부 |
| 슈퍼관리자가 아무것도 갖지 않은 id를 지운다 | 슈퍼관리자 | 없는 id를 지우기 | 대상 없음으로 거부 |

수정 권한만 가진 사람을 줄로 두는 이유는, 지우기가 수정과 다른 문이라는 것을 못박기
위해서다. 소유한 행을 지우는 요청 중에도 이 문을 쓰는 것과 수정 문을 쓰는 것이 갈린다.

이 어댑터에는 hard-delete가 없다. 지우기는 지우는 중이라고 표시하고 나머지는 뒤에서 돈다.
완전히 지우는 문이 생기면 권한도 따로 걸리므로 그때 줄을 더한다.

## 아직 적지 않은 것

어느 시나리오도 부르지 않는 어댑터 호출이다. 실행 결과가 이 목록을 함께 낸다.

deployment가 소유하는 행의 호출은 필드마다 절을 따로 둘 때 적는다.

- 리비전: `add_revision`, `get_revision`, `search_revisions`, `admin_search_revisions`,
  `search_revision_resource_slots`, `batch_load_revisions_by_ids`
- 복제본과 경로: `get_replica`, `search_replicas`, `admin_search_replicas`, `search_routes`,
  `update_route_traffic`, `batch_load_replicas_by_ids`, `batch_load_routes_by_ids`
- 접근 토큰: `create_access_token`, `get_access_token`, `delete_access_token`,
  `search_access_tokens`, `bulk_delete_access_tokens`, `batch_load_access_tokens_by_ids`
- 배포 정책: `get_policy`, `upsert_policy`, `search_policies`,
  `batch_load_policies_by_endpoint_ids`
- 자동 확장 규칙: `create_rule`, `get_rule`, `update_rule`, `delete_rule`, `search_rules`,
  `bulk_delete_rules`, `batch_load_auto_scaling_rules_by_ids`
