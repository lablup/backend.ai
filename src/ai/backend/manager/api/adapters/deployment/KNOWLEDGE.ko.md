# deployment adapter: 배경

규칙은 상위 디렉터리의 `AGENTS.md` 에 있다. 이 문서와 실행 결과가 어긋나면 문장을 먼저 의심한다.

deployment 는 프로젝트 스코프에 생성된다. 생성 권한은 프로젝트에 적용되고, 생성된 뒤에는 그 deployment 자체에 적용된다. 전역 살펴보기와 전체 리비전 새로 고침만 전역 역할이 보호한다.

deployment 가 own 하는 row(리비전, 복제본과 경로, 배포 토큰, 배포 정책, 자동 확장 규칙)는 이 절에 적지 않는다. 그것들은 자기 스코프가 없고 소유 deployment 로 인가되므로, 필드마다 절을 따로 둔다.

## 생성

집행을 끄는 시나리오는 도메인과 반대 결과를 가진다. 이 호출은 역할이 아니라 권한 그래프가 보호하므로 스위치가 적용된다. 도메인 문서의 같은 시나리오와 짝을 이루는 부분이다.

생성은 배포 정책 row 를 함께 작성한다. 전략을 고르는 갈래가 셋이라 각각을 row 로 둔다. 순차 설정을 준 경우, 청록 설정을 준 경우, 어느 설정도 주지 않고 전략 이름만 준 경우다.

리비전 보관 개수는 요청이 정하지 못한다. 생성이 값을 고정한다.

이름이 공백뿐인 요청과 복제본 수가 음수인 요청은 row 로 두지 않는다. 요청 타입이 이미 차단하므로 adapter 가 보장하는 동작이 아니다.

응답의 기본 배포 전략은 요청이 무엇을 골랐든 순차로 온다. 고른 전략은 배포 정책 쪽에 담긴다.

## 읽기

없는 id 는 superadmin 과 그 밖의 사용자에게 다른 것으로 거부된다. 권한 검사가 먼저 실행되고 없는 row 에는 부여된 권한도 없으므로, 그 검사를 통과하는 superadmin 만 대상 없음을 본다. 아래 절의 없는 id row 도 모두 같다.

현재 리비전 조회는 읽기 두 번을 이어 붙인 것이다. deployment 를 읽을 권한만 있고 리비전을 읽을 수 없는 사용자는 없으므로, 두 번째 호출이 따로 차단하는 것이 없다는 것을 row 로 둔다.

## 살펴보기

살펴보는 호출이 셋이다. 전역 살펴보기는 역할이 보호한다. 프로젝트 살펴보기는 그 프로젝트에, 내 것 살펴보기는 호출자 자신의 스코프에 부여된 읽기 권한이 보호한다. 내 것 살펴보기도 범위만 좁히지 않는다. 살펴보기에 따로 적용되는 권한은 없다. 살펴보기와 읽기가 같은 비트를 본다.

## 수정

이름이 공백뿐인 요청은 row 로 두지 않는다. 생성과 같이 요청 타입이 차단한다.

요청 타입이 선호 도메인 이름과 배포 전략을 받지만 수정 경로가 그 둘을 사용하지 않는다. 지금은 조용히 버려진다. row 를 작성하기 전에 버릴 것인지 사용할 것인지 정한다.

## 옵션 교체

옵션은 배포 단계를 실행하는 processor 가 얼마나 기다리고 몇 번까지 다시 실행하는지다. 생성할 때 자원 그룹의 기본값을 복사해 두므로 비어 있는 적이 없고, 자원 그룹 쪽이 나중에 변경되어도 따라 움직이지 않는다. 그래서 이미 있는 deployment 의 값을 변경하는 호출은 이것뿐이다.

교체는 병합하지 않는다. 부분 수정으로 읽히기 쉬운 자리라 보내지 않은 값이 사라진다는 것을 row 로 따로 둔다.

processor 이름은 살아 있는 등록 목록과 대조한다. 시나리오는 이름을 리터럴로 적지 않고 등록된 항목에서 읽는다.

응답에는 deployment 전체가 아니라 교체한 옵션만 담긴다. 다른 호출과 검사 범위가 다르다.

## 리비전 활성화

활성화는 리비전이 그 deployment 의 것인지 보지 않는다. 다른 deployment 의 리비전 id 를 보내면 어떻게 되어야 하는지 정하고 row 를 적는다.

전체 새로 고침은 일부만 성공하는 것이 설계다. 하나가 실패해도 나머지가 실행된다는 것을 row 로 둔다.

## 복제본 수 맞추기

맞추기는 요청 안에서 끝나지 않는다. 응답은 시작했다는 것뿐이고, 복제본이 실제로 뜨는 것은 다른 곳에서 확인한다.

## 삭제

수정 권한만 가진 사용자를 row 로 두는 이유는, 삭제가 수정과 다른 호출이라는 것을 고정하기 위해서다. own 하는 row 를 삭제하는 요청 중에도 이 호출을 사용하는 것과 수정 호출을 사용하는 것이 갈린다.

이 adapter 에는 영구 삭제가 없다. 삭제는 삭제 중이라고 표시하고 나머지는 뒤에서 실행된다. 완전히 삭제하는 호출이 생기면 권한도 따로 적용되므로 그때 row 를 추가한다.

## 리비전

리비전은 deployment 가 own 하는 row 다. 자기 스코프가 없고 소유 deployment 의 권한으로 열린다. 추가는 deployment 에 생성 권한을, 읽기와 살펴보기는 읽기 권한을 요구한다. 현재 리비전 조회, 활성화, 전체 새로 고침은 위 절에 있다. 리비전을 고르지만 쓰는 값은 deployment 의 현재 리비전이다.

리비전 하나는 여러 계층을 쌓아 만든다. 모델 마운트 경로의 기본값, 인퍼런스 런타임 종류의 기본값, 리비전 프리셋, 모델 vfolder 안의 설정 파일, 그리고 요청이다. 뒤 계층이 앞 계층을 우선 적용한다. 요청의 하위 설정은 전부 생략할 수 있고, 생략한 항목은 앞 계층이 채운다.

### 추가

응답에는 추가된 리비전만 담긴다. 다음 넷은 응답에 드러나지 않거나 미리 저장할 수 없어 row 로 두지 않는다.

- 자동 활성은 deployment 의 배포 중 리비전을 변경한다.
- 보관 개수를 넘으면 오래된 리비전이 삭제된다. 현재 리비전과 배포 중 리비전은 세지 않고 남긴다.
- 마운트 권한을 지정하지 않으면 호출자가 모델 vfolder에 가진 권한이 붙는다. 응답의 마운트 설정에 권한 칸이 없다.
- vfolder 파일을 읽는 인퍼런스 런타임 종류이면 vfolder 안의 정의 파일이 한 계층이 된다. 변형의 write spec 이 그 성질을 받지 않아 미리 저장할 수 없다.

모델 정의는 마운트 경로 기본값이 모델 하나를 항상 넣으므로 비지 않는다. 이름을 채우는 계층이 없으면 그 모델이 검증에서 차단된다.

마운트 권한은 두 계층으로 제한된다. 모델 vfolder는 호출자가 그 vfolder에 가진 권한을 넘지 못하고, 덧붙인 vfolder는 그 vfolder 자체의 권한을 넘지 못한다. 첫 번째에서 넘는 쪽만 row 로 둔다. 두 번째는 덧붙인 vfolder seed 가 생길 때 추가한다.

모델 vfolder 권한은 호출자가 그 vfolder에 가진 권한 비트로 읽는다. 읽기는 읽기 전용, 수정은 읽기와 쓰기, 영구 삭제는 삭제까지로 마운트된다. 읽기가 없으면 vfolder를 찾을 수 없다는 이유로 차단된다. superadmin 은 권한을 받지 않아도 vfolder에 모든 비트를 가진다. vfolder 읽기 권한이 없는 사용자를 보는 row 말고는, 권한 검사를 통과하는 추가 row 가 모두 vfolder 읽기 권한을 가진다.

자원 슬롯을 채우는 계층은 프리셋과 vfolder 안의 설정 파일뿐이다. 인퍼런스 런타임 종류은 모델 정의만 제공한다.

보관 개수는 생성이 고정한 값이다.

### 읽기

리비전을 읽는 호출은 소유 deployment 를 먼저 찾고 그 deployment 의 권한을 본다. 그 조회는 없는 id 와 볼 수 없는 id 를 한 가지로 거부한다. 모든 검사를 통과하는 superadmin 만 대상 없음을 본다.

### 살펴보기

자원 슬롯 살펴보기는 리비전 하나를 참조하는데도 전역 역할이 보호한다. 그 리비전을 읽을 수 있는 사용자가 슬롯은 볼 수 없다는 뜻이라, 짝을 두어 고정한다.

## 배포 토큰

토큰은 deployment 가 own 하는 row 다. 영구 삭제는 단건과 여럿 모두 소유 deployment 의 영구 삭제 권한을 요구한다.

### 여럿 영구 삭제

여럿 연산은 호출 전체를 거부하지 않는다. 처리한 row 는 처리된 목록에, 처리하지 못한 항목은 id 와 이유를 실패 목록에 담는다.
